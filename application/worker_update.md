# Кадровое обновление в рабочем потоке

`TryBeginFrame` резервирует физический слот и `FrameKey` до публикации `OnUpdate`. Один callback выполняется на worker `TaskSystem`; при backpressure он не вызывается повторно. Пока нет объявлений доступа пользователя, следующее обновление мира допускается только после полного Extract предыдущего кадра. Подготовка immutable render data и GPU могут продолжаться параллельно.

`OnPostUpdate` выполняется на worker TaskSystem ровно один раз после семантического завершения Engine Update текущего FrameKey. Порядок: `OnUpdate → Engine Update → OnPostUpdate → FinalizePostUpdate (structural commit) → Extract`. Следующее обновление допускается после завершения всех читателей Extract. В этой эксклюзивной фазе можно менять принадлежащий приложению World и публиковать deferred structural commands; runtime владельца World обязан применить их в FinalizePostUpdate до Extract. Незавершённые detached записи запрещены. Подготовка immutable render data и GPU могут перекрываться со следующим обновлением.

Миграция: замените `void OnDraw() override` на `void OnPostUpdate() override`; старого callback больше нет, старый override не компилируется. OnPostUpdate не является native render callback. Engine::Draw и rendering API сохраняют свои имена. Операции с окном из прежнего OnDraw перенесите в `RunOnMainThread`.

Оконные API доступны на main. Из `OnUpdate` и `OnPostUpdate` используйте `RunOnMainThread`; основной цикл продолжает события и ограниченные порции команд, пока worker ожидает. `RequestShutdown` сам передаёт закрытие на main; `IsShutdownRequested` читает опубликованный атомарный флаг. `GetInputSnapshot` в обоих callbacks предоставляет размеры окна/framebuffer и монотонный номер snapshot, зафиксированные на main перед публикацией текущего callback. Snapshot не меняется до следующего допуска кадра. Пользовательские input-данные из оконных callbacks требуют собственного immutable snapshot либо синхронизации: оконные callbacks могут исполняться одновременно с обоими callbacks. Прямой доступ к изменяемому состоянию Window из worker запрещён.

Объект callbacks внутреннего FrameLoop обязан переживать Stop. Application хранит его вместе с runtime, а не на стеке одной итерации событий. Наследник Application обязан закончить Run до разрушения собственных полей. При закрытии сначала останавливается MainExecutor: pending команды получают SKIPPED, ожидающие workers освобождаются. Затем Engine отменяет queued user callbacks, запрашивает отмену ECS и ждёт semantic completion, CPU tails и GPU. Исключение OnUpdate или OnPostUpdate сохраняется в runtime error channel и передаётся вызывающему Run; commit/Extract этого кадра отменяются; следующий Run создаёт новое поколение кадров. Queued OnPostUpdate при Stop пропускается, уже начавшийся callback дренируется перед освобождением его target.

Публикация задач и структурные изменения не используют блокирующее ожидание child work на workers. Долгая монолитная OnUpdate всё ещё занимает один worker и не разбивается scheduler автоматически. Приоритеты main-команд учитывают происхождение кадра; выбор команд ограничивает голодание при высокой нагрузке.
