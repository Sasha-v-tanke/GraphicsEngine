## Владение миром

`World` владеет сущностями, хранилищами компонентов и зарегистрированными системами. Дескрипторы сущностей содержат поколение: уничтожение сущности делает все прежние дескрипторы её слота недействительными, даже если слот позднее используется повторно.

Уничтожение сущности немедленно удаляет все её компоненты. Удаление компонента делает ссылки на него недействительными. Создание и удаление других сущностей или компонентов не гарантирует неизменный порядок обхода запросов.

Отложенные структурные изменения резервируют идентификаторы сущностей и помещают в очередь команды создания, уничтожения, добавления и удаления компонентов. Они становятся видимыми только после применения очереди. Если ожидающее отложенное создание добавляет новый слот, немедленное создание сущностей блокируется до применения очереди. При резервировании свободного слота отложенным созданием этот слот сразу удаляется из списка свободных, поэтому немедленное создание не может занять тот же идентификатор.

## Фазы изменения

`RunSystems()` последовательно выполняет обработчики. `RunSystems(taskSystem)` запускает граф задач с зависимостями в рабочих потоках переданного `TaskSystem`, дожидается всех задач данного мира и применяет структурные команды. Для параллельного варианта каждой системе необходим устойчивый идентификатор планирования. Координатор должен исполняться в управляющем потоке; вызов из любого рабочего потока `TaskSystem` отклоняется до публикации задач, чтобы рабочий поток не ожидал собственный пул. `World` и `TaskSystem` должны существовать до возврата из вызова. Во время исполнения вызывающий код не должен конкурентно обращаться к изменяемому состоянию `World`. Явный `structuralOrder` управляет только порядком объединения структурных изменений; он не меняет порядок обработчиков или обычных чтений и записей компонентов. Системы без структурного порядка не могут собирать структурные команды.

Обработчики систем могут непосредственно изменять существующие компоненты. Структурные операции (`CreateEntity()`, `DestroyEntity()`, `AddComponent<T>()` и `RemoveComponent<T>()`) запрещены во время работы систем: используйте отложенные операции. `RunSystems()` собирает команды и применяет их после завершения всех зарегистрированных систем. Параллельные производители должны использовать отдельные `DeferredStructuralCommandBuffer`. До запуска рабочих потоков вызывающий код объявляет каждого производителя и его максимальное число создаваемых сущностей через `BeginDeferredStructuralPhase()`. Мир заранее резервирует идентификаторы в устойчивом порядке `producerOrder`, поэтому порядок завершения потоков не влияет на идентификаторы. Буферы публикуются после объединения задач. Для самостоятельного управления фазами предусмотрен явный `ApplyDeferredStructuralChanges()`.

Создавайте буферы рабочих потоков системы внутри соответствующего обработчика до запуска рабочих задач. Они захватывают структурный порядок данной системы. При применении команды систем сортируются по ключу (`structuralOrder`, непосредственные команды перед рабочими, `producerOrder`); порядок производителей внутри одной системы должен быть уникальным. Внешние независимые буферы образуют отдельную фазу после команд систем. Буфер рабочего потока публикуется после завершения его задач, но до возврата из обработчика. Буфер принадлежит конкретному вызову обработчика: следующий вызов не может его опубликовать, а внешний буфер нельзя передать во владение системе.

До `RunSystems()` объявляйте производителей системы через `BeginDeferredStructuralPhase()`, задавая `SystemOrder` равным структурному порядку их системы. Идентификаторы резервируются по (`SystemOrder`, `Order`) до начала всех обработчиков; значения порядка производителей могут повторяться в разных системах. Обработчики создают сущности через запланированные буферы; общая перегрузка `DeferCreateEntity()` при выполнении систем запрещена. Новый план нельзя начать внутри обработчика.

У каждого обработчика свой контекст отложенных изменений. Его собственные команды и команды рабочих потоков накапливаются до общего завершения. При ошибке любого обработчика структурные команды текущего `RunSystems` и неиспользованные резервы отбрасываются. Зависимые задачи отменяются; независимые задачи завершаются до повторного выбрасывания исходного исключения. Уже выполненные обычные записи компонентов не откатываются. Ранее поставленные внешние команды остаются доступны для явного применения. После ошибки перед повторным созданием сущностей необходим новый план резервирования.

При применении и откате системы свободные слоты сортируются по индексу до следующего выделения. Поэтому возврат неиспользованных резервов из разных рабочих потоков не меняет идентификатор следующей сущности. Применение запрещено, пока некоторый буфер удерживает резервы создания и не был опубликован или уничтожен. Неудачное применение сохраняет резервы: можно опубликовать либо уничтожить буфер и повторить попытку.

## Контракт доступа

Системы с `SystemSchedule` используют устойчивые идентификаторы и необязательные ограничения `Before` и `After`. Все системы планируемого мира должны объявлять идентификатор; старые регистрации сохраняют последовательный режим. Неизвестные зависимости, повторные идентификаторы и циклы отклоняются до выполнения обработчиков. Сначала явные ограничения определяют канонический топологический порядок с выбором минимального готового идентификатора. Конфликты чтение/запись, запись/чтение и запись/запись добавляют рёбра в этом порядке; чтение/чтение зависимость не создаёт. Так явные ограничения соблюдаются без скрытой привязки разрешения конфликтов к порядку регистрации. `structuralOrder` остаётся отдельным ключом применения.

Декларации доступа должны точно описывать все чтения и записи компонентов, включая обращения задач, созданных обработчиком. Обработчик обязан дождаться своих задач до возврата. Необъявленные обращения и синхронизация внешнего изменяемого состояния, общего для обработчиков, остаются ответственностью вызывающего кода.

`AddComponent<T>()`, `GetComponent<T>()` и обработчики запросов требуют существующую сущность; устаревшие дескрипторы отклоняются. `HasComponent<T>()` и `RemoveComponent<T>()` возвращают `false` при устаревшем дескрипторе или отсутствии данных.

`Query<T...>(callback)` — текущий callback API: отбирает живые сущности с полным набором компонентов, передаёт `Entity` и ссылки (const при чтении const World). Он не возвращает range. По умолчанию пропускает disabled entities и любые disabled required components; Get/Has продолжают видеть сохранённые значения. Активный query reader запрещает `Queue*` commit до завершения обхода; это не разрешение на конкурентные произвольные записи. Ссылки на компоненты нельзя сохранять через удаление/replacement или использовать вне объявленной фазы доступа.

Внутренние основы доступа по областям реализованы в `internal/access_coordinator.*`. Они не устанавливаются как публичные интерфейсы и не заменяют существующий планировщик систем `World`. Правила владения и исполнения приведены в [документации внутреннего координатора](#внутреннее-планирование-доступа-к-областям-данных).

## Иерархия сущностей

Структурированные связи родителей и детей, `TopologyEpoch`, удерживаемые снимки топологии и отложенное изменение родителя описаны в [контракте иерархии](#иерархия-сущностей-и-topologyepoch). Получение снимка не делает обычные операции `World` потокобезопасными и ограничивает структурные изменения до освобождения всех удерживаемых доступов.

Внутренний runtime использует неблокирующий [SystemRun](#неблокирующее-выполнение-систем): сильное владение World, двухфазную публикацию и завершение после всех producer tickets. Синхронная host-обёртка использует тот же параллельный execution core и сохраняет запрет worker Wait.

Выборочный расчёт производных матриц и контракт для extraction/culling описаны
в [документации TransformResolver](#выборочный-world-transform-resolver).


## Отложенный пользовательский structural intake

`World::QueueCreateEntity`, `QueueDestroyEntity`, `QueueAddComponent<T>`, `QueueRemoveComponent<T>`,
`QueueSetEnabled`, `QueueSetComponentEnabled<T>` и `QueueReparent` только записывают команды.
Они используют существующий World, generational `EntityReference` и producer buffers, без второго storage.
Это foundation для EntityRef/Scene API (FEATURE-0082), а не новый Builder. Pending create не виден `Query`/`Get`.
`GetStructuralState` различает pending create, alive, pending destroy и destroyed; stale/foreign mutation отвергается.

Локальные повторные Add/Remove и implicit Replace отклоняются при enqueue. Между producers commit проверяет
весь детерминированно объединённый пакет на shadow metadata/topology до первой мутации; конфликт отбрасывает
пакет и reservations целиком. Повторный Destroy в одном commit идемпотентен. Компоненты, в том числе move-only,
не копируются при preflight. Ошибки синхронного commit — проектные исключения; async SystemRun публикует FAILED/Error.

`CommitPending` разрешён только host в quiescence без активных producer buffers/topology readers и не реентерабелен.
SystemRun автоматически публикует initialization перед системами и команды систем после их полного retirement.
Failed/cancelled systems сохраняют прежний discard/ticket protocol. Detached worker не получает права на intake.
Ни commit, ни producers не ожидают дочернюю работу на worker.

Preflight даёт strong guarantee относительно живых сущностей/компонентов/topology. Если allocation/конструктор
падает уже при apply, возможен изменённый префикс: World явно poisoned до teardown, дальнейшие systems, mutation,
Query/Get и topology extraction отвергаются. Это не успешная публикация и не обещание rollback in-place writes.
`IsExecutionPoisoned` доступен для диагностики. Ошибка preflight сама по себе не требует poison.

Legacy immediate `CreateEntity/AddComponent` и `Defer*` сохраняют прежнюю семантику совместимости, включая
replace/partial apply в чисто legacy пакете. При смешивании с Queue-командами весь commit проходит preflight.
Enabled metadata публикуется здесь; фильтрация Query реализована в FEATURE-0083, range iteration и World::ForEach — в FEATURE-0084. EntityRef реализован в FEATURE-0082.
Имена и fluent Scene-фасад реализованы в FEATURE-0082, runtime Scene capability integration относится к FEATURE-0087.

Пользовательский фасад `EntityRef` и его scope/lifetime описаны в [docs/about/entity_ref.md](../docs/about/entity_ref.md); пример — [создание сущности](../docs/how_to/create_entity.md).

## Иерархия сущностей и `TopologyEpoch`

`World` хранит лес иерархий: у каждой сущности не более одного родителя, связи с детьми упорядочены, а локальное преобразование задано аффинной матрицей. `EntityReference` содержит идентификатор `World` и дескриптор `Entity` с поколением. Ссылки на разные миры не смешиваются, даже если индекс и поколение совпадают. `GetEntityReference` лишь добавляет идентификатор мира к дескриптору: действительность проверяется при чтении снимка или применении команды. Это позволяет ссылаться на сущности, создание которых запланировано отложенно. Прежний интерфейс компонентов с `Entity` не меняется; новый интерфейс иерархии требует идентификатор мира.

`AcquireTopologySnapshot()` выдаёт удерживаемый доступ к топологии, а не копию дерева. Копии снимка, диапазоны детей и итераторы удерживают один и тот же доступ; их можно передавать рабочим потокам и освобождать в другом потоке. Пока доступ действует, топология и локальные матрицы неизменны. Он сохраняет собственное хранилище после уничтожения `World`, но не компоненты и не право обращаться к уничтоженному миру. Для работы с компонентами по-прежнему необходимы действительный срок жизни `Scene`/`World` и разрешённый доступ к ECS. Попытка получить доступ одновременно с разрешённой публикацией структурных изменений завершается `INVALID_STATE`.

Операции создания и удаления сущностей, добавления и удаления компонентов, `SetLocalTransform` и применение структурной очереди отклоняются с `INVALID_STATE`, пока есть удерживаемые доступы. Применение очереди проверяет это **до извлечения команд**: после освобождения читателей можно повторить попытку без потери команд. Нет ожидания под мьютексом и блокирования рабочих потоков. Вызывающий код должен завершить обходы и освободить все удерживаемые доступы до управляемого применения структурных изменений; нельзя хранить итератор между фазами моделирования. По-прежнему действует внешний контракт единственного владельца операций и системного доступа к `World`. Удерживаемый доступ не делает все методы `World` потокобезопасными.

`DeferReparent(child, parent, mode)` и перегрузка с локальным буфером производителя участвуют в прежнем детерминированном объединении команд по порядку систем, производителей и публикации. Пустой родитель означает корень. Создание и уничтожение также используют существующие команды; непосредственные операции допустимы только в разрешённой структурной фазе. Перед изменением связей проверяются самоссылки, циклы, устаревшие ссылки, ссылки на другой мир и режим. Одна команда применяется атомарно. В чисто legacy `Defer*` пакете при ошибке уже успешно применённый префикс сохраняется, ошибочная команда удаляется, а оставшиеся остаются в очереди — как в прежнем контракте структурных команд. Эпоха увеличивается после каждого успешного создания, удаления или изменения родителя; операция без изменения и ошибка эпоху не меняют. Несколько команд становятся видимыми читателям только после выхода из применения очереди. Переполнение эпохи и идентификатора мира отклоняется.

`KEEP_LOCAL` сохраняет локальную матрицу. `KEEP_WORLD` до изменения связей вычисляет прежнюю мировую матрицу и новую локальную как `inverse(parentWorld) × oldWorld`. Матрицы должны быть конечными и аффинными. Необратимая матрица родителя либо результат с некорректными числами вызывают `INVALID_ARGUMENT`. Перед публикацией проверяется обратная композиция: допустимая погрешность каждого элемента не превышает `1e-4 × max(1, abs(oldWorldElement))`. Если локальная матрица с элементами `float` не сохраняет мировое преобразование с этой точностью, команда отвергается без изменения связей и эпохи. Полная матрица сохраняет сдвиговые деформации, которые нельзя точно представить произвольным сочетанием переноса, вращения и масштаба.

`GetWorldTransform` — последовательная эталонная реализация с итеративным обходом, без кэша и скрытых записей; стоимость линейна по глубине. При удалении сущности её непосредственные дети становятся корнями с прежними локальными матрицами; поддеревья не удаляются рекурсивно. Повторно использованный слот не наследует связей или локальной матрицы.

Это базовый контракт иерархии `World`. Для `Queue*` и смешанных пакетов действует preflight/poison протокол [structural intake](#отложенный-пользовательский-structural-intake), а не legacy partial apply. Производные матрицы и адаптивный обход реализованы отдельными внутренними слоями ниже. Локальная матрица не заменяет `NRenderer::TransformComponent`: extraction композирует hierarchy world matrix × `ComposeTransform(TransformComponent)` и сохраняет точное affine значение. Отдельных мьютексов сущностей и потоковой загрузки сцен этот слой не добавляет.

## Неблокирующее выполнение систем

`NEcs::NInternal::PrepareSystems(shared_ptr<World>, TaskSystem&, onFinished)` захватывает эксклюзивный run guard до построения графа и создаёт heap state с неизменяемым порядком, стабильными invocations, handles, dependency arrays, owner lease и completion sink. Callback registry принадлежит World. RunSystems(TaskSystem&) использует этот execution core через private borrowed lease и отдельный host completion; worker guard сохраняется. RunSystems() остаётся последовательной удобной обёрткой.

PreparedSystemRun — move-only владелец публикации. Получите SystemRun и свяжите cancellation до Start. Start разрешён один раз и может завершиться синхронно, включая пустой граф. Уничтожение незапущенного PreparedSystemRun завершает его CANCELLED. Уничтожение наблюдающего SystemRun не отменяет работу. TryGetOutcome не ждёт и не потребляет результат.

Начальный outstanding=1 удерживает публикацию. Перед каждым Submit регистрируется contribution; при отказе он откатывается. Принятые wrappers исполняются до retirement даже при ошибке: system exception сохраняется внутри run, downstream callbacks пропускаются. Runtime не вызывает TaskSystem::Cancel для скрытых handles и сохраняет пул до drain. Финальный Submit не нужен: последний участник выполняет commit/rollback и cleanup.

DeferredStructuralCommandBuffer получает ticket до передачи производителю и удерживает run/World до Submit или уничтожения буфера. Адрес invocation стабилен. Буфер, передаваемый за пределы system callback, должен соответствовать producer, объявленному через BeginDeferredStructuralPhase (включая нулевой EntityCreateCount). Submit после возврата системы кладёт batch в owning invocation; cancelled run всё равно потребляет буфер и уничтожает payloads при retirement. Ticket предоставляет только право собирать команды в этом буфере, не произвольный доступ к компонентам. Dynamic fan-out с mutable World вне объявленного протокола требует отдельной TaskGroup/access интеграции.

Terminal означает завершение всех nodes/tickets, deterministic merge, structural commit либо discard, очистку temporary payloads и снятие World guard/lease. Cleanup/destructors и completion sink исполняются вне coordination locks. Cancellation не откатывает in-place component writes и не прерывает running callback. Ошибка выбирается после quiescence: publication error, затем первая system error в graph.Order, затем cancellation. Commit/cleanup failure даёт FAILED; World после неуспешного commit/cleanup закрыт для нового execution до teardown. Ошибки cleanup не должны давать ложный COMPLETED.

Гарантии терминальных переходов `TaskSystem` определяются самим исполнителем, а не ECS-адаптером. Этот adapter не меняет generic executor protocol и не гарантирует безопасное принудительное завершение не возвращающегося пользовательского кода.

## Внутреннее планирование доступа к областям данных

Изолированный координатор работает на стороне владельца. Он не изменяет `World`, существующие `Read<T>/Write<T>`, `TaskSystem`, пользовательские обратные вызовы и барьеры графического устройства. Адаптер ECS и представления областей данных связывают координатор с планированием систем. Одно лишь объявление доступа здесь не делает произвольные ссылки на изменяемый `World` безопасными.

### Контракт владельца и области доступа

Для каждого ограниченного периода выполнения или набора задач используется один координатор. Владелец хранилища регистрирует `DataDomainKey{OwnerId, TypeId, Generation}` вместе с токеном строгого удержания времени жизни. Все обращения к изменяемой области должны проходить через один координатор. Владелец гарантирует, что токен действительно удерживает нужное хранилище, устойчивую индексацию и идентификаторы сущностей или ресурсов: планировщик не может самостоятельно проверить жизнь произвольных объектов. Структурные изменения, повторное использование идентификаторов и перераспределение порций требуют отсутствия активных обращений и строго более нового поколения; устаревшие и незарегистрированные ключи отклоняются. Разные владельцы и типы независимы. Поколение разграничивает время жизни, но не позволяет объявить независимыми две версии одной и той же живой изменяемой памяти.

`CHUNK` обозначает разрешённый полуоткрытый диапазон в том же пространстве индексов, что и `ENTITY` и `ENTITY_SET`, а не непрозрачный номер порции. Множества сортируются, очищаются от повторов, а одинаковые области доступа объединяются до допуска. Пустые множества, пустые диапазоны и переполнения — ошибки. `RESOURCE` обозначает логический идентификатор ресурса: разные ресурсы независимы. Пересечение разных пространств и `UNKNOWN` консервативно трактуются как пересечение всей области. `WHOLE_STORAGE` пересекается со всем в своей области. Развёртывание поддерева относится к будущему разрешителю с устойчивой топологией; он может использовать вычисленные множества и диапазоны либо безопасный запасной `UNKNOWN`.

Для пересекающихся областей совместимы только `READ/READ`. `WRITE` и `EXCLUSIVE` исключают все пересекающиеся обращения. Совместимость описывает только доступ к памяти; смысловой порядок производитель–потребитель должен задаваться явными зависимостями операций.

### Порядок и исполнение

`Schedule` сериализует допуск и присваивает монотонный `OperationKey` с идентификатором владельца. Для каждой операции все конфликтующие незавершённые предшественники и явно указанные предыдущие ключи становятся неизменяемыми рёбрами. Учитываются и ожидающие операции: писатель всего хранилища, ожидающий читателей, не может быть обогнан новыми читателями. Все рёбра направлены к ранее допущенным операциям, поэтому ссылки на будущие операции, чужие ключи и циклы структурно отклоняются. Одновременные производители упорядочиваются при допуске; для воспроизводимого порядка публикации вызывающий код должен публиковать операции в нужной последовательности либо объявить зависимости. Время завершения не меняет порядок уже допущенных конфликтов.

Для операций `WAITING` задачи в `TaskSystem` ещё нет. При продвижении готовая работа отмечается `QUEUED` под краткой блокировкой метаданных, после чего `TaskSystem::Submit` вызывается вне этой блокировки. Пользовательские обратные вызовы работают без блокировок координатора. Не используются ожидание зависимостей внутри задач, задачи опроса, отдельные мьютексы на сущность или каскад отмен исполнителя. При одном рабочем потоке обработчик может опубликовать конфликтующего последователя и вернуться; завершение исходной задачи откроет допуск следующей.

Операция обязана закончить все объявленные обращения до возврата. Отделённая работа не наследует её область доступа. Объединение динамических дочерних задач остаётся ответственностью `TaskGroup` или адаптера: координатор не предполагает, что дочерняя задача завершилась вместе с родительской.

### Ошибки, отмена и время жизни

Отмена ожидающей задачи атомарна относительно перехода `QUEUED` → `RUNNING`. `Cancel` для уже выполняющейся или конечной операции возвращает `false`: начатый доступ нельзя отозвать. Логическое состояние `CANCELLED` не освобождает резерв доступа: и сохранённые, и уничтожаемые в данный момент захваты удерживают его до окончания своих деструкторов. Замена области и допуск конфликтующих операций отдельно проверяют отсутствие активных обращений, а не только статус. Работа, допущенная одновременно с отменой, ещё видит отменённого предшественника и консервативно отменяется; новый допуск возможен после окончательного освобождения. Оболочка отменённой задачи может выполниться без действий, удерживая только слабое состояние, но не выполняя пользовательский код.

Ошибка сохраняется как `exception_ptr`. Ошибочные или отменённые предшественники отменяют зависимые операции, не открывая частично готовые данные. Ошибка также закрывает новый допуск; владелец обязан восстановить данные и создать новый координатор или период исполнения. Уже допущенные независимые задачи могут завершиться. Отката изменений памяти на месте нет. Ошибка публикации записывается как `FAILED` и обрабатывается по тем же правилам.

`Stop` вызывается только управляющим потоком: закрывает допуск, отменяет ожидающие операции, дожидается работающих обработчиков и уничтожения их захватов, после чего освобождает токены областей в управляющем потоке вне блокировок метаданных. Он не останавливает общий исполнитель и не вызывает его `WaitIdle()`; исполнитель должен пережить координатор. До уничтожения координатора управляющий код обязан присоединить конкурентных производителей. Ни обработчик, ни деструктор его захватов не может останавливать или уничтожать собственный координатор во избежание ожидания самого себя. В остальных случаях деструкторы захватов могут проверять состояние, планировать и отменять работу, пока допуск разрешён. Никакие пользовательские захваты или токены областей не уничтожаются под блокировкой метаданных, включая отклонённый допуск и замену области.

История состояний, зависимостей и конфликтов сохраняется до уничтожения координатора. Текущая реализация удерживает историю всего периода и просматривает её при допуске и продвижении; в плотном наборе конфликтов затраты квадратичны. Это не постоянный неограниченный реестр `World`. Завершайте ограниченный период после освобождения всех обращений и создавайте координатор для следующего; старые ключи считаются чужими. Оптимизации индексированных границ опасностей и освобождения требуют измерений и не входят в исходный контракт. Диагностика указывает точную область и диапазон, вызвавшие каждое ребро; явные зависимости отдельно доступны через `GetDependencies`.

## Адаптивный обход иерархии

`AdaptiveBatchPlanner` — внутренний планировщик обхода `TopologySnapshot`. Он не выдаёт доступ к произвольным компонентам World: вызывающая сторона отдельно обеспечивает admission и footprints через AccessCoordinator либо исключительное владение данными. Пользовательский ECS API и вычисление transforms не входят в этот модуль.

`ScheduleTraversal(snapshot, roots, mode, operation, policy)` возвращает обычный `TaskGroupHandle`. Все корни должны быть живыми, принадлежать snapshot и задавать непересекающийся лес. Проверка ссылок и оценок стоимости выполняется до публикации первой задачи. Иерархия не копируется; на время работы удерживается существующий topology lease. План содержит только результаты, счётчики готовности и оценки стоимости, индексированные стабильными slots snapshot.

### Режимы и результаты

- `TOP_DOWN`: callback получает неизменяемый результат родителя; для выбранного корня — `nullptr`.
- `BOTTOM_UP`: callback получает результаты всех непосредственных детей в порядке topology siblings. Последний готовый ребёнок выполняет продолжение reduction итеративно; worker не ожидает других задач.
- `INDEPENDENT`: callback не получает parent/child results.

Callback возвращает владеющее значение произвольного типа. Один узел имеет ровно одного writer. Ссылки на входные parent/child results действуют только внутри callback; их нельзя сохранять или передавать detached jobs. Callback может исполняться параллельно с другими ветвями; внешние побочные записи требуют отдельного disjoint ownership и не откатываются при ошибке.

`TraversalOutput<T>` — одноразовый слот публикации. `TryAcquire(tasks)` выдаёт immutable `TraversalResults<T>` только после `COMPLETED`. До completion и после failure/cancellation доступ к staging results отсутствует. Полученный результат сохраняет старую Entity identity; повторно использованный slot с другой generation не совпадает с ним. TaskSystem должен оставаться живым при наблюдении группы/output. `RunSerial` даёт итеративный reference с теми же правилами результата и порядка зависимостей.

Topology lease и execution captures освобождаются до terminal publication группы. Готовые результаты сами по себе не удерживают topology. Планировщик и исходный World могут быть уничтожены во время обхода: snapshot владеет независимым hierarchy storage. Структурная публикация в ещё живой World запрещена до освобождения snapshot. Результаты, возвращаемые callback, должны владеть своими данными; сохранённая ссылка на компонент не становится access lease.

### Пакеты и стоимость

Пакет описывает диапазон siblings либо выбранных корней. Малые ветви объединяются; большой диапазон делится только при наличии независимого остатка и свободного packet budget. Однодетная цепочка обрабатывается итеративно одним пакетом без task-per-node. Динамические descendants используют `SpawnInGroup`; внешняя публикация закрывается через `SealGroup` после допуска первого пакета. `WaitGroup` разрешён только host-потоку.

Максимум активных/queued пакетов выбирается из количества узлов, worker count и верхней границы `MaxPacketsPerWorker`; при одном worker создаётся один пакет. Target учитывает общую оценку работы, `TargetPacketsPerWorker`, минимальное полезное время пакета, измерение первых callback каждого пакета и стоимость scheduling предыдущих запусков. `EstimateWork` — необязательная чистая функция положительной конечной относительной стоимости узла. Неверные значения/overflow отклоняются до исполнения. Feedback принадлежит planner, но текущий run владеет им независимо от lifetime planner.

Метрики: число посещённых узлов, число пакетов, пиковое число активных/queued пакетов, wall time внутри пакетов, время публикации задач и последний target в work units. Счётчики времени не являются эксклюзивным CPU profiler: время пакета включает его локальное scheduling. Оценка стоимости не меняет observable порядок parent/child зависимостей и sibling reduction.

Исключение callback/spawn переводит TaskGroup в failure; pending работа отменяется, running работа дренируется. Отмена кооперативная, проверяется между узлами и шагами reduction. Незавершённые результаты не публикуются. Ошибка допуска закрывает созданную группу и освобождает lease; отказ динамического spawn не теряет уже учтённых участников.

### Проверки производительности

`BM_AdaptiveTraversal/<shape>/<workers>/<iterations>` использует существующий benchmark runner. Shapes: 0 balanced, 1 star, 2 bamboo, 3 random, 4 skewed; workers=0 — serial reference, 1/4 — TaskSystem; iterations=0/10000 — мелкий/тяжёлый callback с неодинаковой стоимостью узлов. Время включает планирование и ожидание completion, создание World вынесено за измерение.

Локальный Release, AppleClang 21, 4096 узлов, медиана трёх повторов (это измерение, не переносимый порог):

| Shape | Serial, ms | 1 worker, ms | 4 workers, ms | Пакетов, 4 workers |
| --- | ---: | ---: | ---: | ---: |
| Balanced, heavy | 107.801 | 109.570 | 30.288 | 9 |
| Star, heavy | 107.827 | 107.832 | 30.683 | 13 |
| Bamboo, heavy | 108.318 | 108.243 | 108.221 | 1 |
| Random, heavy | 108.604 | 110.689 | 33.887 | 10 |
| Skewed, heavy | 108.352 | 111.248 | 30.800 | 13 |

На мелком callback serial занимал 0.078–0.144 ms, один worker — 0.107–0.170 ms; абсолютный overhead — примерно 25–35 µs на 4096 узлов. Для такого workload планировщик сохранял один пакет; ускорение не заявляется. Глубокая цепочка не имеет независимых ветвей и также не должна ускоряться от увеличения workers.

## Выборочный world transform resolver

`TransformResolver` — внутренний потребитель удерживаемой топологии, без новых
пользовательских API. `LocalTransform` принадлежит `TopologyState`; производный
`WorldTransformCache` принадлежит resolver. Локальная матрица и её `LocalRevision`
изменяются только в разрешённой фазе записи World. Никакие другие компоненты не
получают обязательных entity revisions.

### Расчёт и версии

`ScheduleResolve(topology, requiredEntities, tasks)` собирает объединение запросов
и всех их предков. Повторы устраняются; чужие, пустые и устаревшие дескрипторы
отклоняются до отправки задач. Resolver связан с одним World и допускает один
незавершённый расчёт. Разные resolver могут независимо читать одну топологию.

Выборка передаётся в `AdaptiveBatchPlanner` в parent-first порядке. Проекция
связей содержит только выбранные узлы: соседние невостребованные поддеревья не
посещаются. Для `BOTTOM_UP` проекция дополнительно читает direct sibling links
выбранных родителей, сохраняя topology order для некоммутативной reduction;
resolver использует `TOP_DOWN` и этого дополнительного прохода не делает. Рабочие задачи читают неизменяемый результат родителя и записывают
собственное значение. Разбиение идёт по независимым поддеревьям с ограниченным
числом пакетов; deep bamboo обрабатывается итеративно без рекурсии и worker Wait.

Узел stale, если отличается `AppliedLocalRevision`, `AppliedParent` или
`AppliedParentWorldRevision`. У stale узла пересчитывается матрица и увеличивается
его собственная `WorldRevision`. Первый stale узел после актуального родителя
является dirty root; его выбранные потомки видят новую parent revision. Отдельно
изменённый ребёнок проверяется даже при cache hit родителя. Локальная запись
никогда не обходит потомков ради invalidation. `KEEP_LOCAL` меняет edge stamp;
`KEEP_WORLD` дополнительно меняет local revision. Обе версии включают era;
исчерпание всей пары отклоняется до изменения состояния.

Cache хранит не более одного значения на слот сущности, проверяя также World и
поколение. Снимок результата содержит только текущую ancestor closure, поэтому
несколько последовательных view-запросов переиспользуют общий cache, но не
возвращают отсутствующие в текущем запросе объекты. Матрицы доступны через
`ReadResolved(tasks)` только после успешного `GetCompletion()`. Getter ничего
не вычисляет и не публикует. Сохранённые результаты неизменяемы, не удерживают
World и могут пережить его уничтожение, новые расчёты и повторное использование
entity slots.

### Отказ и время жизни

Все значения вычисляются в staging storage. После успешного завершения группы
продолжение проверяет результаты и заранее выделяет map nodes только для stale
значений. Затем единая секция публикации заменяет cache без выделений памяти.
Исключение или отмена не открывают частичный результат; предыдущий cache остаётся
доступен следующему расчёту. `TaskSystem::Cancel` не допускает отмену уже
исполняемого продолжения публикации. При отмене `GetCompletion()` ещё выполняющийся
обход следует отдельно завершить через `GetTraversal()` либо `WaitIdle()`.

Topology lease удерживается до retirement всех traversal callbacks, исключая
параллельное изменение local matrices/links. Отмена продолжения не освобождает
lease работающего обхода. TaskSystem должен пережить планирование, отмену и
наблюдение. Ошибка отправки продолжения также может оставить выполняющийся обход;
его освобождение гарантируется retirement callbacks, а не возвратом из Schedule.
Уничтожение facade resolver не отменяет отправленный расчёт.

### Извлечение и culling

Потребитель объединяет required entities всех views и включает предков камер и
объектов. До completion запрещено использовать новый результат. Для culling
required означает все кандидаты, чьи bounds ещё не гарантированно консервативны,
а не только видимые в предыдущем кадре объекты: иначе движущийся из-за родителя
объект может ошибочно остаться невидимым. Bounds строятся по матрицам завершённого
текущего запроса; если актуальных bounds нет, объект сохраняется кандидатом.
Отсутствующий объект в `ResolvedTransforms::Get()` вызывает ошибку, без fallback
к старой матрице. Старый immutable результат соответствует старому состоянию;
он не является доказательством актуальности в новом кадре.

Incremental extraction уже использует resolver при полной invalidation: объединяет
камеры и render-кандидатов с предками, а затем передаёт точную affine матрицу
до backend. `TransformComponent` сохраняет роль плоского render-смещения;
результат равен hierarchy world matrix × `ComposeTransform(TransformComponent)`.
Один и тот же перенос нельзя дублировать в обоих представлениях. Culling/bounds
пока отсутствуют, поэтому required включает всех кандидатов. Shear не раскладывается
в TRS. Граница публикации и immutable снимки описаны в [Renderer](../renderer/README.md#иерархия-и-матрицы).

### Стоимость и проверки

Closure строится за `O(C log C)` с map на C выбранных сущностей; матричные
умножения выполняются только для stale узлов. Cache-hit всё равно проверяет
stamps всей closure. Planner пока выделяет временный массив по максимальному
слоту World (`O(S)`), как и полный traversal; выборка не обещает O(C) памяти.
Это явно отделено от отсутствия обхода невостребованных поддеревьев.

Регрессии `TransformResolver.*` покрывают parent/child/both edits, независимый
stale child, cache hits, несколько views, 10k bamboo, reparent modes, переполнение
матрицы с неизменным опубликованным cache, отмену, lifetime и поколения.
`AdaptiveTraversal.*` проверяет исходный полный обход и его порядок reduction.

## Enabled state и фильтрация (FEATURE-0083)

`EntityRef::Enable/Disable` и `EnableComponent<T>/DisableComponent<T>` записывают команды в
существующий structural intake. Новая сущность и каждый добавленный компонент включены по умолчанию.
Отключённое значение не уничтожается: `GetComponent`, `TryGetComponent`, `HasComponent` и scoped `Get`
работают независимо от флагов; это относится и к пустым tag-компонентам. Дети не отключаются автоматически.

`IsEnabled` и `IsComponentEnabled<T>` отражают committed state, независимо друг от друга.
Pending entity ещё не enabled; запрос её component flag выдаёт `NOT_READY`, как чтение компонента.
Для отсутствующего committed T фасад выдаёт `NOT_FOUND`. Для pending structural commands ошибка
может диагностироваться при preflight commit; Add можно сразу сопровождать DisableComponent того же T.
Повторные включения/отключения идемпотентны по состоянию; последовательные toggles одного producer
применяются в порядке enqueue, разные producer — по существующему deterministic merge protocol.
Ошибка/отмена системы отбрасывает её commands; изменение не публикуется в обход commit barrier.

```cpp
entity.Disable();
entity.DisableComponent<Velocity>();
scene.CommitPending(); // Только quiescent host: runtime использует свои safe commit boundaries.
```

Текущий callback `Query<T...>(callback)` использует `SkipDisabled` по умолчанию.
Отбор проверяет флаг сущности и всех required T; выключенный нерелевантный компонент не исключает сущность.
Явный второй параметр — `EQueryEnabledPolicy::SKIP_DISABLED` либо `INCLUDE_DISABLED`.
Range и `World::ForEach` используют общий обход и поддерживают fluent выбор политики:

```cpp
for (auto [entity, position, velocity] : world.Query<Position, const Velocity>()) {
    // EntityRef, Position&, const Velocity&; компоненты не копируются.
    position.Value += velocity.Value;
}
world.ForEach<Position, const Velocity>(
    [](NEcs::EntityRef entity, Position& position, const Velocity& velocity) { /* ... */ });
std::as_const(world).Query<Position>().IncludeDisabled().ForEach(
    [](NEcs::EntityRef entity, const Position& position) { /* ... */ });
```

Первый `begin()` фиксирует membership и адреса компонентов; повторный `begin()` использует тот же snapshot.
`ForEach` проходит этот же input range. Legacy `Query<T...>(callback)` продолжает передавать `Entity`;
descriptor `ForEach` также принимает явно типизированный legacy callback для совместимости.
На текущем unordered_map backend стоимость создания snapshot — O(entity slots × required types),
память — O(matches × required types), шаг итератора — O(1). Нет копий компонентов и обещания порядка итерации.
Baseline и новый API сравниваются в `benchmarks/traversal/query.cpp` (legacy/ForEach/range, workers 1/2/8).

Range не удерживает World. Descriptor/итератор отвергают использование после уничтожения World,
смены structural/phase epoch, завершения invocation или с постороннего потока. Итератор не продлевает
жизнь range. Активный snapshot запрещает физические structural writes, commit и начало нового run;
queued Create/Add/Remove/Destroy/Enable по-прежнему допустимы и не меняют текущий membership.
Перед commit на owner нужно уничтожить активные ranges; не начатый descriptor будет инвалидирован commit.
На выходе invocation её readers автоматически снимаются, даже при исключении или сохранённом range.
Ссылки из tuple нельзя сохранять за эту границу: C++ `T&` сам по себе не является проверяемым handle.

В system `Query<const T>` требует Read или Write, `Query<T>` требует Write; const World всегда выдаёт const T&.
EntityRef из const World сохраняет read-only capability даже при копировании. Обход на owner разрешён
только в quiescent phase. Внутренний `ScopedBatchContext::Query/ForEach` использует тот же core:
пересекает resolved entity scopes required типов, Read указывается через const T, Write через T.
AccessCoordinator и scheduler не меняются; query не добавляет dependencies или worker waits.

Внутренний `ScopedView::ForEach` тоже использует SkipDisabled, а `.IncludeDisabled()` включает оба вида
отключения. Enabled bits фиксируются вместе с resolved batch до worker execution; `Get` не фильтруется.
Queued изменения невидимы текущему обходу, commit запрещён при активных Query/scoped readers.
Flags проверяются в той же фазе, что component access; произвольный конкурентный доступ к World не разрешён.

Все три пути Renderer extraction используют default Query: после commit отключённые renderables,
их Transform либо камеры не попадают в следующий RenderWorld. Enabled commit помечает change domains
для перестройки incremental membership; ранее опубликованный снимок остаётся неизменным.
Callbacks OnEnable/OnDisable, physics integration и hierarchy cascade не добавлены.

Host-owner нового Query descriptor и EntityRef — поток создания World. Без активной зарегистрированной
ECS invocation разрешён только этот поток; проверки не ограничиваются распознаванием TaskSystem workers.
В зарегистрированной invocation действуют её прежние scoped/read-write права, независимо от потока исполнения.
Остальные legacy World методы и явный producer protocol этим ограничением не заменяются.
