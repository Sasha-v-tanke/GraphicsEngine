# Система задач

Модуль `Thread` содержит независимые от графической реализации средства планирования вычислительных задач. Его публичная часть — `TaskSystem`: пул рабочих потоков для выполнения `TaskFunction` по графу зависимостей. Он не зависит от рендеринга, ресурсов, оконной системы или графического интерфейса.

Динамические группы и неблокирующий fan-in описаны в [контракте TaskGroup](#динамические-группы-задач).

## Жизненный цикл задачи

```text
CREATED -> WAITING -> READY -> RUNNING -> COMPLETED
                         |          |
                         |          +-> FAILED
                         +------------> CANCELLED
```

`CREATED` — внутреннее состояние до публикации. После возврата `Submit()` пользователь видит только `WAITING`, `READY`, `RUNNING` и конечные состояния.

- `WAITING` — задача опубликована, но ждёт успешного завершения зависимостей.
- `READY` — все зависимости завершены, задача в очереди рабочего пула.
- `RUNNING` — задача исполняется в рабочем потоке.
- `COMPLETED` — обработчик завершился без исключения.
- `FAILED` — исключение обработчика преобразовано в `ErrorInfo`.
- `CANCELLED` — явная отмена либо отмена вследствие ошибки или отмены зависимости.

## Дескрипторы и время жизни

`TaskHandle` — устойчивый дескриптор опубликованной задачи. Он привязан к идентичности конкретного экземпляра `TaskSystem` и непрозрачному состоянию задачи; локальный числовой идентификатор служит только для диагностики. Дескриптор другого `TaskSystem`, в том числе уничтоженного планировщика и нового планировщика по тому же адресу, не считается локальным и отклоняется как неправильный аргумент.

Конечное состояние доступно через `TaskHandle`, пока вызывающий код удерживает дескриптор и соответствующий `TaskSystem` существует. При переходе в конечное состояние планировщик сразу освобождает данные исполнения: обработчик, рёбра зависимостей и захваченные ресурсы, удерживаемые только обработчиком. Запись реестра переносится в связанный список освобождения без выделения памяти и удаляется из активного поиска при следующей очистке. Поэтому память планировщика не растёт пропорционально общему числу задач за всю его жизнь.

После уничтожения `TaskSystem` сохранённый `TaskHandle` становится устаревшим значением. Его нельзя использовать с новым или другим планировщиком.

`TaskContext` живёт только во время вызова обработчика; сохранять его и использовать после возврата из `TaskFunction` запрещено. Он некопируем и непереносим: scheduler, task identity и WorkerIndex неизменяемы. `TaskContext::GetTask()` возвращает дескриптор текущей задачи, `TaskContext::GetWorkerIndex()` — устойчивый индекс исполняющего её рабочего потока. `IsCurrentInvocation(scheduler)` проверяет совпадение scheduler, Task ID и worker с текущим invocation; контекст соседнего worker не проходит проверку даже пока оба обработчика активны.

`TaskSystem` фиксирует `WorkerCount` при создании. Ноль нормализуется до единицы; после запуска число потоков неизменно и доступно через `GetWorkerCount()`. `WorkerIndex` находится в диапазоне `[0, GetWorkerCount())` и остаётся постоянным для рабочего потока.

## Зависимости и порядок

Набор зависимостей копируется при `Submit()`. Изменение исходного контейнера, из которого создан `std::span`, не меняет граф. После публикации рёбра задачи неизменны: дополнительные ограничения порядка выражаются новой задачей с собственными зависимостями.

Повторные дескрипторы отклоняются с `INVALID_ARGUMENT`. Для списков до 16 элементов проверка использует прежний поиск без временной памяти. Для больших списков после проверки владельцев сортируется отдельная копия ID: `O(D log D)` сравнений и `O(D)` временной памяти, без перестановки исходных зависимостей. Эта подготовка предшествует выдаче ID, linking и accounting: отказ выделения памяти на проверке не меняет граф или `NextTaskId`.

Задача становится `READY`, только когда все предшественники достигли `COMPLETED`. Если один из них достиг `FAILED` или `CANCELLED`, зависимая задача отменяется. Поддерживаются несколько предшественников и несколько последователей: для объединения зависимостей хранится `RemainingDependencies`, а для разветвления — список зависимых задач каждой исходной. Завершающийся предшественник атомарно уменьшает счётчик зависимых; последний, доведший счётчик до нуля, переводит задачу в `READY`.

Выполняющаяся задача может создавать новые через `TaskContext::Spawn()`. Если дочерняя зависит от существующих задач, передавайте их через `Spawn(function, dependencies)` вместо ожидания в рабочем потоке.

Порядок независимых `READY` задач не гарантирован. Между рабочими задачами порядок выражается графом, а не блокирующим ожиданием внутри обработчика.

Готовые задачи распределяются по локальным очередям рабочих потоков. Публикации из рабочего потока сначала попадают в его очередь; внешние потоки используют отдельную общую очередь входящих задач с низкой конкуренцией. Свободный рабочий поток сначала проверяет свою очередь, затем общую, затем забирает работу из очередей других потоков. Потоки не закреплены за кадрами, подсистемами и стадиями рендеринга: любой свободный поток может выполнить любую готовую задачу. Поток приложения не исполняет рабочие обработчики, а только публикует задачи, наблюдает состояния и может блокироваться в `Wait()` или `WaitIdle()`.

## Граница обработки ошибок

Исключения не выходят за пределы рабочего потока. Они преобразуются в `ErrorInfo`:

- `NCommon::Exception` — исходные код `std::error_code` проекта и сообщение.
- `std::system_error` — исходный `std::error_code` и сообщение.
- `std::exception` — `EError::UNKNOWN` и `what()`.
- Неизвестное исключение — `EError::UNKNOWN` и общее диагностическое сообщение.

`GetError()` возвращает `std::optional<ErrorInfo>`. Для `COMPLETED` и `CANCELLED` ошибки нет.

`FAILED` и `CANCELLED` — конечные состояния. По умолчанию ошибка либо отмена предшественника каскадно отменяет всех ещё не выполняющихся последователей. Уже выполняющаяся задача не прерывается принудительно: её обработчик доходит до конца, а результат фиксируется как `COMPLETED` или `FAILED`.

## Потокобезопасность

`Submit()`, `GetStatus()`, `GetError()`, `Cancel()`, `Wait()` и `WaitIdle()` допускают одновременные вызовы из внешних потоков. `Wait()` и `WaitIdle()` из рабочего потока собственного `TaskSystem` запрещены: для создания дочерней работы используйте `TaskContext::Spawn()`, для порядка — зависимости.

`Wait(task)` блокирует вызывающий поток до конечного состояния; при `FAILED` или `CANCELLED` он не выбрасывает исключение. Результат следует проверить через `GetStatus()` и `GetError()`.

`WaitIdle()` блокирует до отсутствия активных и выполняющихся задач. Отмена снимает готовую задачу с очереди до её финализации. Конечные состояния могут по-прежнему удерживаться внешними дескрипторами.

Горячий путь `READY` не имеет одного общего мьютекса для всех операций: локальные очереди, общая входная очередь и состояния отдельных задач синхронизируются отдельно. Рабочий поток захватывает переход `READY -> RUNNING` через локальное состояние задачи; финализация фиксирует конечное состояние, изменения графа и accounting под блокировкой реестра. Уничтожение пользовательских захватов выполняется отдельно, без внутренних блокировок. Конечные записи помещаются в связанный список освобождения и удаляются при целевой очистке вне пути завершения каждой задачи.

Свободные потоки ждут на `condition_variable` с предикатом готовой работы или остановки. Публикация очереди и атомарного счётчика готовых задач согласована под мьютексом очереди; handshake с мьютексом ожидания и уведомление выполняются после снятия блокировок реестра, состояния и очереди, предотвращая потерю пробуждения. При ожидании простоя нет активного цикла опроса.

Измерения находятся в `benchmarks/task`: `BM_TaskSystemDependencyValidation` измеряет отдельно проверку зависимостей, `BM_TaskSystemDependencySubmitLatency` — только время `Submit` на завершённых предшественниках (без времени исполнения/`Wait`); `BM_TaskSystemIndependentThroughput` измеряет пропускную способность независимых готовых задач, `BM_TaskSystemFanInLatency` — задержку от фактического завершения последнего предшественника до завершения зависимой задачи.

Отладочные сборки при изменениях графа или состояния выполняют облегчённую проверку инвариантов ацикличного графа: повторных рёбер, обратных связей предшественник/последователь и согласованности `RemainingDependencies`. Эти проверки не входят в горячий путь выпускаемой сборки.

## Владение и остановка

`TaskSystem` владеет рабочими потоками. Конструктор запускает пул, а при исключении во время создания одного потока уничтожает уже созданные.

Деструктор переводит пул в состояние остановки. После этого новые задачи через `Submit()` или `TaskContext::Spawn()` отклоняются. Задачи `READY` и `WAITING` отменяются и убираются как пометки очередей, отмена распространяется на их последователей. Уже захваченные рабочими потоками задачи `RUNNING` не прерываются насильно и завершают обработчик. Остановка пробуждает рабочие потоки и присоединяет все созданные потоки; после уничтожения `TaskSystem` его рабочие потоки не остаются.

Подробные гарантии публикации конечного результата, уничтожения захватов и каскадной отмены изложены в [контракте финализации задач](#финализация-задач-в-tasksystem).


## Динамические группы задач

`CreateTaskGroup()` создаёт `TaskGroupHandle`, привязанный к экземпляру `TaskSystem`. `SubmitToGroup(group, function, dependencies)` принимает внешнюю работу только в состоянии `OPEN`. `SealGroup()` закрывает внешнюю публикацию. Выполняющийся участник может вызвать `TaskContext::SpawnInGroup(function, dependencies)` и после seal: принадлежность наследуется от текущей invocation, каждый потомок учитывается до публикации. Обычный `Spawn()` остаётся независимой работой.

Состояния: `OPEN → SEALED → COMPLETED / FAILED / CANCELLED`. Пустая группа завершается только после seal. Открытая группа учитывается в `WaitIdle()`, поэтому каждую созданную группу нужно закрыть через seal или cancel. `WaitGroup()` разрешён только вне compute workers, возвращается после завершения всех участников и уничтожения их execution captures; исход читается через `GetGroupStatus()` и `GetGroupError()`. Handle сохраняет identity, но методы требуют живого владельца. Использовать TaskContext после invocation запрещено.

`SubmitAfterGroup()` публикует обычную задачу с зависимостью от completion группы. Ранняя регистрация и terminal publication сериализованы тем же registry lock; поздняя регистрация наблюдает сохранённый outcome. Группа не занимает worker и не создаёт polling/finalizer tasks. Completion gate выделяется при создании; готовые continuations публикуются через intrusive очередь без выделения памяти. Ошибка или отмена группы отменяет continuation, включая позднюю.

Первая ошибка участника сохраняется в `GetGroupError()`. Failure и отмена до старта закрывают spawn, отменяют pending участников и дренируют running. `CancelGroup()` идемпотентен; running код может проверить `IsGroupCancellationRequested()`, принудительного прерывания нет. Поздняя ошибка running участника имеет приоритет над отменой. Пока участники дренируются, наблюдаемый статус — `SEALED`. `StopWorkers` закрывает также пустые незапечатанные группы. Отказ Submit откатывает рёбра и reservation после уничтожения неопубликованного payload; успешные прежние участники продолжают работать.

Группы не принадлежат кадрам, ECS или пользовательским coroutine. Их следует использовать для крупных CPU packets и рекурсивного fan-out; они не расширяют разрешённые области доступа к World и не заменяют Job<T>. Нельзя создавать циклическую зависимость участника от continuation собственной группы. `TaskGroup` не расширяет гарантии общего terminal/READY path при ошибках выделения памяти.

## Финализация задач в `TaskSystem`

Этот раздел фиксирует гарантии освобождения пользовательских захватов при завершении и отмене задач.

### Уничтожение захватов

`TaskSystem` уничтожает принадлежащие ему захваты вызываемых объектов **вне блокировок реестра, состояния задачи и очередей готовых задач**. Это относится к обычному завершению и ошибке, прямой и зависимой отмене, остановке планировщика, немедленно отменённой задаче из `Submit()`, а также к отклонённой подготовке или откату `Submit()`.

После публикации конечного состояния `TaskHandle` больше не удерживает вызываемый объект. При этом дополнительные копии вызываемых объектов или захваченных данных, находящиеся вне `TaskSystem`, остаются ответственностью пользователя.

### Финализация и публикация результата

Внутренний признак финализации (`FINALIZING`) предотвращает повторный запуск и повторную отмену, пока уничтожаются данные исполнения задачи. До завершения уничтожения `GetStatus()` продолжает возвращать прежнее **неконечное** состояние. Результат `GetError()` публикуется согласованно с конечным исходом задачи.

`Wait()` и `WaitIdle()` не завершают ожидание раньше уничтожения принадлежащих задаче захватов. При успешном завершении предшественника зависимая работа становится доступной к исполнению **после** уничтожения его захватов.

### Каскадная отмена и ожидание

Если предшественник завершился неуспешно, новый зависимый узел может быть отменён уже во время его финализации (`FINALIZING`). Поэтому завершение `Wait()` для отменённого потомка **не означает**, что захваты всех предшественников уже уничтожены. Чтобы дождаться полного освобождения ресурсов графа задач, необходимо явно дождаться соответствующих дескрипторов либо вызвать `WaitIdle()` после закрытия допуска новых задач.

Каждый пакет каскадной отмены самостоятельно удерживает состояние `State` до публикации конечного исхода и снятия вклада в счётчик незавершённой работы. Обход пакета выполняется итеративно; блокировки отдельных `State` не вкладываются друг в друга.

### Повторный вход из деструкторов

Деструктор захваченного объекта может вызвать `Submit()`, `GetStatus()` или `Cancel()` для **другой** задачи. Во время остановки планировщика `Submit()` отклоняется, поэтому деструктор должен обработать соответствующее исключение. Вызов `Cancel()` для уже финализируемой задачи идемпотентен и не ждёт окончания финализации, выполняемой другим потоком.

Деструкторы захватов должны быть `noexcept` и завершаться за конечное время. Не поддерживаются ожидание собственной задачи, вызов `WaitIdle()` из собственной финализации и уничтожение пула рабочих потоков из обратного вызова. Отмена действительно исполняющейся задачи в состоянии `RUNNING` по-прежнему возвращает ошибку `INVALID_STATE`.

### Границы реализованного

Рёбра выделяются стабильным массивом в состоянии зависимой задачи до публикации. Каждое ребро включено в два двусвязных списка: входящих рёбер потомка и исходящих рёбер предшественника. Удаление снимает оба набора связей за `O(1)`, без поиска по ID или перемещения соседей. Под блокировкой реестра raw endpoints удерживаются реестром или локальным владельцем; перед передачей потомка в cleanup/ready пакет создаётся сильный pin. Массив не перемещается после linking и освобождается только после удаления всех связей.

Графовая часть отмены использует отдельную встроенную FIFO-очередь ещё не обработанных состояний. Узел захватывается один раз, каждое затронутое ребро удаляется один раз; обработанная часть пакета не обходится повторно при добавлении работы из TaskGroup. Сложность — `O(Vc + Eincident)`, где учитываются также входящие рёбра из неотменяемых предшественников; для всего DAG — `O(V + E)`, внутренний стек — `O(1)`. Обход и unlink не выделяют память. Уничтожение пользовательских захватов выполняется отдельно от графового обхода и может повторно входить в executor по описанному выше контракту.

Регрессии запускаются отдельными CTest-процессами с timeout. Цепочки из 200 тысяч узлов проверяются при `WorkerCount=1/2/8`, широкий fan-in — на 100 тысячах общих потомков. Эти heavy-сценарии выполняются также в Debug: локальные проверки мутаций не запускают полный аудит реестра.

### Отказ выделения памяти

`Submit` подготавливает callable, стабильный массив рёбер, состояние, диагностику и запись реестра до первой графовой мутации. Ошибка подготовки не публикует задачу, рёбра или вклад в outstanding. ID монотонны; пропуски после отказа допустимы, переполнение отклоняется. Владельцы пользовательских данных переживают блокировку реестра при раскрутке стека.

После commit linking, счётчики, финализация, отмена и публикация READY не выделяют память. READY хранится во встроенном двусвязном списке State: local pop — LIFO, injected pop и steal — FIFO. У каждого узла одна membership и один вклад в ReadyTaskCount; отмена удаляет его за O(1). Реестр удерживает raw queue entry; pop под Q получает strong pin **до** unlink и освобождения Q, затем отдельно захватывает S. Очередь не содержит self-owning shared_ptr.

Порядок блокировок: G → S или G → Q; S не вкладывается в другой S или Q. W защищает ожидание CV по атомарному предикату `ReadyTaskCount != 0 || stopping`; уведомление и handshake с W выполняются после освобождения G/S/Q. Поэтому отменённые узлы не оставляют semaphore permits, а новая READY-публикация не теряет пробуждение.

Worker перехватывает только исключения пользовательского callable. Если построение ErrorInfo не удалось, публикуется FAILED с OUT_OF_MEMORY и пустым Message. Terminal tail не повторяется в catch; ошибки внутренних примитивов/инвариантов завершают процесс. Успешный terminal status, outgoing detach, remaining и ready publication выполняются в одной G-транзакции. Outstanding снимается после уничтожения захватов и публикации готовых потомков. Каждый terminal notify выполняется до следующего пользовательского деструктора в cleanup batch.

Fault suite перебирает отказы подготовки Submit/TaskGroup и запрещает новые allocations при completion/fan-out, ErrorInfo fallback, cancellation и ready publication. Отдельная регрессия удерживает pop lease через Cancel, очистку реестра и уничтожение пула. Debug использует локальные noalloc-проверки мутаций; полный аудит вызывается явно в тестах/диагностике.


### Проверка DAG в Debug

`ValidateMutationLocked` проверяет изменённый State за O(1): головы списков, кэшированные степени, remaining и допустимость состояния. `ValidateEdgeLocked` проверяет изменяемое ребро и соседние backlinks за O(1) до unlink и после link. Debug-степени обновляются вместе с intrusive hooks под G. Для пачки Submit/Cancel стоимость проверок пропорциональна затронутым вершинам и рёбрам; общий предшественник с большим fan-out не сканируется при каждом новом потомке. Проверки не выделяют память и сохраняют no-throw commit из FIX-0004. Они не берут два S одновременно и не пересекаются с Q.

`ValidateDagFullLocked` запускается явно через private test/diagnostic access под G. Он сначала строит множество активных State и адресов их stable edge storage, затем проверяет endpoints, обе цепочки, уникальность prerequisites/dependents, remaining и состояния. Неизвестные адреса отвергаются до dereference; live edge обязан присутствовать ровно в обоих списках. Учитываются FINALIZING, group gates и terminal entries до retirement drain. Полный аудит может выделять память и не вызывается в prepare/commit/terminal path автоматически.

Регрессии через test-only adapter временно повреждают remaining, головы/обратные ссылки, endpoint, ID, cached degree и уникальность prerequisite, затем восстанавливают граф под G. Счётчики посещений отделяют локальные проверки от явного полного аудита. `BM_TaskSystemDagValidation` измеряет Debug admission и Cancel на одинаковых chain/fan-out inputs.
