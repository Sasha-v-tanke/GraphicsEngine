# Динамические группы задач

`CreateTaskGroup()` создаёт `TaskGroupHandle`, привязанный к экземпляру `TaskSystem`. `SubmitToGroup(group, function, dependencies)` принимает внешнюю работу только в состоянии `OPEN`. `SealGroup()` закрывает внешнюю публикацию. Выполняющийся участник может вызвать `TaskContext::SpawnInGroup(function, dependencies)` и после seal: принадлежность наследуется от текущей invocation, каждый потомок учитывается до публикации. Обычный `Spawn()` остаётся независимой работой.

Состояния: `OPEN → SEALED → COMPLETED / FAILED / CANCELLED`. Пустая группа завершается только после seal. Открытая группа учитывается в `WaitIdle()`, поэтому каждую созданную группу нужно закрыть через seal или cancel. `WaitGroup()` разрешён только вне compute workers, возвращается после завершения всех участников и уничтожения их execution captures; исход читается через `GetGroupStatus()` и `GetGroupError()`. Handle сохраняет identity, но методы требуют живого владельца. Использовать TaskContext после invocation запрещено.

`SubmitAfterGroup()` публикует обычную задачу с зависимостью от completion группы. Ранняя регистрация и terminal publication сериализованы тем же registry lock; поздняя регистрация наблюдает сохранённый outcome. Группа не занимает worker и не создаёт polling/finalizer tasks. Completion gate выделяется при создании; готовые continuations публикуются через intrusive очередь без выделения памяти. Ошибка или отмена группы отменяет continuation, включая позднюю.

Первая ошибка участника сохраняется в `GetGroupError()`. Failure и отмена до старта закрывают spawn, отменяют pending участников и дренируют running. `CancelGroup()` идемпотентен; running код может проверить `IsGroupCancellationRequested()`, принудительного прерывания нет. Поздняя ошибка running участника имеет приоритет над отменой. Пока участники дренируются, наблюдаемый статус — `SEALED`. `StopWorkers` закрывает также пустые незапечатанные группы. Отказ Submit откатывает рёбра и reservation после уничтожения неопубликованного payload; успешные прежние участники продолжают работать.

Группы не принадлежат кадрам, ECS или пользовательским coroutine. Их следует использовать для крупных CPU packets и рекурсивного fan-out; они не расширяют разрешённые области доступа к World и не заменяют Job<T>. Нельзя создавать циклическую зависимость участника от continuation собственной группы. `TaskGroup` не расширяет гарантии общего terminal/READY path при ошибках выделения памяти.
