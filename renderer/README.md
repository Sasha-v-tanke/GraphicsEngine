# Подготовка рендеринга

`Renderer` отвечает за независимое от конкретного графического интерфейса представление данных для рендеринга. Изменяемое состояние моделирования остаётся в `NEcs::World`; подготовка использует только неизменяемый `RenderWorld`.

`RenderGraphBuilder` преобразует смысловые объявления проходов и ресурсов в неизменяемый план исполнения кадра. Время жизни импортированных ресурсов, проверки и подключение исполнителя описаны в [контракте графа рендеринга](#граф-рендеринга).

## Компоненты рендеринга

`TransformComponent`, `CameraComponent` и `RenderableComponent` — высокоуровневые компоненты `World`. `RenderableComponent` ссылается на логические ресурсы сетки и материала через типизированные `ResourceHandle`, но не содержит физических дескрипторов графического интерфейса.

## Извлечение снимка

Контрольная точка рисования `Engine` публикуется до извлечения данных. `IFrameRuntime::Extract()` выполняется после `Update N`; следующее обновление `Engine` допускается лишь после завершения извлечения.

Извлечение читает `World` через постоянный интерфейс запросов и копирует только данные рендеринга в текущий `FrameExecutionSlot`. Для объектов получаются версионные `ResourceLease` из `Resources`. Явная политика `RenderableComponent::ReadinessPolicy = SKIP_OBJECT` исключает объект, если необходимая сетка или материал ещё недоступны; ожиданий загрузки или GPU upload нет.

`RenderWorld::GetResourceDiagnostics()` сохраняет причины skip, identity, состояние и ошибку ресурса на момент извлечения. Правила фиксации решений, диагностики и времени жизни описаны в [разделе готовности ресурсов](#готовность-ресурсов).

Итоговый `RenderWorld` содержит устойчивые идентификаторы объектов, данные камер, преобразования и удерживаемые версии ресурсов. `Renderer` получает диапазоны только для чтения и не обращается к изменяемому `World` данного кадра.

После извлечения `Update N+1` может выполняться одновременно с рендерингом кадра N. Логическая выгрузка или повторная загрузка ресурса после извлечения запрещает новые получения, но не заменяет уже удерживаемые версии `RenderWorld N`.

### Готовность ресурсов

#### Политика MVP

`RenderableComponent::ReadinessPolicy` явно выбирает `EResourceReadinessPolicy::SKIP_OBJECT`. Если необходимая сетка или материал не готовы, весь объект исключается из RenderWorld. Это выбранная политика для текущего frontend; автоматических placeholder, fallback assets или синхронной загрузки нет. Будущая fallback policy может расширить этот контракт, сохранив получение immutable leases и диагностику решений.

Для валидных handles состояния UNLOADED, QUEUED, LOADING, CPU_READY, UPLOADING, FAILED и UNLOADING не дают lease. CPU_READY отдельно не означает разрешение GPU consumer: async loader с uploader публикует READY только после exact upload completion. CPU-only загрузчики сохраняют существующий READY-контракт для backend preparation.

Пустой handle означает отсутствие обязательного ресурса и также даёт skip. Foreign, stale и type-mismatched handles остаются ошибками программирования: extraction fail-fast с object ID, ролью ресурса и slot/generation, как и до введения readiness policy. Неизвестное значение policy отклоняется. Невалидный handle не превращается в ссылку на новый ресурс, занявший тот же slot.

#### Граница снимка

`ResourceManager::Observe<T>()` под одним metadata lock получает состояние, identity, failure и lease конкретной READY-версии. Нет гонки между независимыми GetState/GetFailure/TryAcquire. Копии строк принадлежат наблюдению; lease удерживает immutable CPU/GPU payload. Наблюдение неверного поколения не раскрывает identity или payload заменившего его ресурса. Observe не выполняет I/O, upload или ожидание completion; краткая синхронизация метаданных остаётся частью thread-safe Resources API.

При последовательной extraction каждое наблюдение сразу превращается в объект или диагностику skip. При параллельной extraction наблюдения и leases получаются в фазе сбора входов, до планирования chunks. Chunks читают только захваченные результаты и render-facing компоненты, затем join публикует снимок. READY/retry/unload после этой фазы не меняет уже принятых решений, включая случай, когда chunks ещё не начали исполняться. World остаётся read-only до join по существующему контракту.

Наблюдения разных ресурсов не являются глобальной транзакцией ResourceManager. Каждый ресурс наблюдается атомарно в момент сбора; переходы, совпавшие с самой фазой сбора, могут быть видны последующим наблюдениям. Опубликованный RenderWorld всегда immutable. Renderer::Prepare/SchedulePrepare не опрашивают ResourceManager и не заменяют версии или решения уже извлечённого кадра.

#### Диагностика

`RenderWorld::GetResourceDiagnostics()` возвращает frame-owned записи только о недоступных обязательных ресурсах: object ID, роль MESH/MATERIAL, policy, запрошенный slot/generation и скопированный ResourceStatus. При известном ресурсе доступны logical identity, lifecycle state и исходный ErrorInfo с path/context. Для пустого handle identity/state отсутствуют, Reference равен EMPTY. Ошибка исходного загрузчика сохраняется без изменения и остаётся доступной в старом кадре после retry, unload и Forget.

При двух недоступных ресурсах публикуются обе причины, сначала mesh, затем material. Порядок объектов и объединения chunks совпадает с последовательным обходом World и не зависит от worker completion. Для готовых объектов диагностик нет. Данные принадлежат FrameStorage; нельзя сохранять span после освобождения соответствующего slot. Если диагностика нужна дольше, скопируйте значения.

#### Lifetime и подготовка

Отброшенный объект не создаёт draw command или resource use record. Принятый объект хранит leases конкретных версий; resource use records переносят это владение на границу отправки. Ни unload, ни повторное использование resource slot не инвалидирует уже захваченный payload. CPU/GPU representations освобождаются после последнего lease/use record согласно существующему completion contract. Этот модуль не вводит новую native retirement queue и не меняет ownership backend.

FrameStorage владеет нетривиальными контейнерами диагностики и leases и уничтожает их до reset арены. RenderPlan не добавляет ссылки на эти строки: consumers читают диагностику через живой RenderWorld, а preparation использует только его удерживаемые версии.

#### Проверки

Регрессионные тесты выполняют delayed I/O -> UPLOADING -> READY при трёх активных кадрах, failure/retry и сохранение identity/path, unload/Forget после capture, удержание GPU token отдельным use record, публикацию READY до начала gated chunks и сопоставление serial/parallel diagnostics. Запуски с 1/2/8 workers проверяют прогресс TaskSystem без ожиданий загрузки и независимость результатов от порядка завершения. Отдельные Resources tests проверяют атомарность статуса/lease во время concurrent reload и отсутствие stale/foreign identity leakage.

### Параллельное извлечение

Внутренняя реализация кадра может переопределить `IFrameRuntime::ScheduleExtract()` и вернуть дескриптор общего завершения из `NInternal::ScheduleRenderWorldExtraction()`. Стандартная реализация всё ещё вызывает последовательный `Extract()`. Параллельная функция обходит ссылки на компоненты для рендеринга в порядке сущностей, делит их на порции по умолчанию из 256 элементов и планирует порции через общий `TaskContext`. Размер порции настраивается; отдельная задача на сущность не создаётся. Последовательный вариант сохраняется для небольших нагрузок и эталонных проверок.

Каждая порция зависит от планирующей задачи: при частичном отказе публикации графа рабочие потоки не должны успеть начать чтение `World`. Каждый поток владеет собственным временным вектором и не выделяет память одновременно из общей кадровой арены. Общая задача завершения дожидается всех порций, проверяет ошибки в порядке порций, затем переносит камеры, объекты и удерживаемые версии ресурсов в слот в порядке порций и сущностей. Порядок фактического завершения потоков не меняет снимок. Ошибка порции запрещает публикацию, но сообщается только после окончания всех читателей `World`. Исходные `World` и `Resources` обязаны пережить общее завершение; мир должен оставаться доступным только для чтения. Воспроизводимость требует одинаковых компонентов, состояний готовности и версий ресурсов.

`Engine` планирует продолжение рисования после общего завершения извлечения, не блокируя рабочий поток `TaskSystem`. Допуск `Update N+1` закрыт до начала продолжения. При ошибке объединения рисование отменяется, а `Engine` переходит к обработке ошибки и остановке; кадр освобождается только после завершения всех читателей. Правило действует и с одним рабочим потоком.

## Владение данными кадра

`RenderWorld`, его контейнеры и удерживаемые ресурсы принадлежат поколению `FrameExecutionSlot`, определённому `RenderFrameIdentity`. Нетривиальные объекты кадра уничтожаются при освобождении или аварийном завершении слота до сброса арены. Версии ресурсов сохраняются для всех потребителей процессора и освобождаются на границе времени жизни кадра.

`RenderWorld` также публикует записи об использовании ресурсов кадра, полученные из удерживаемых `ResourceLease`. `FrameSubmission` владеет этими записями и переносит их на границу отправки в графическую реализацию. Таким образом, версия логического ресурса удерживается вплоть до точного завершения работы графического устройства. Извлечение не раскрывает физические объекты реализации, а `Graphics` не зависит от `Resources`.

## Подготовка команд

`Renderer` читает исключительно `RenderWorld`, не обращается к изменяемому миру, не знает о Vulkan и не формирует физических буферов команд.

Начальный путь формирует независимые от графического интерфейса `DrawCommandData`:

```text
RenderWorld -> подготовка видимости и материалов -> сортировка -> группировка -> DrawCommandData
```

Проверка видимости сейчас консервативна: все объекты считаются видимыми для каждой извлечённой камеры. При одинаковом `RenderWorld` результат детерминирован; команды упорядочены по камере, материалу, сетке и идентификатору объекта. Промежуточные данные и итоговый план располагаются в предоставленном вызывающим кодом ресурсе памяти кадра, обычно арене текущего `FrameExecutionSlot`.

### Параллельная подготовка и группы

`Renderer::SchedulePrepare()` разделяет произведение числа камер и объектов на порции через общий `TaskContext`. Консервативная видимость по-прежнему включает все объекты для каждой камеры. Рабочие потоки создают значения команд в локальных векторах; память кадра выделяет только задача общего завершения. После окончания чтений она объединяет порции по индексам, сортирует по тому же ключу камера/материал/сетка/версия/объект, что и последовательный `Prepare()`, а затем отдельно формирует группы.

При ошибке публикации нет; сообщение об ошибке выдаётся только после завершения всех читателей снимка. Все задачи транзитивно зависят от планирующей, чтобы частичная публикация графа не могла запустить подготовку. Нельзя отменять объединение, пока существуют активные читатели.

`RenderPlan::GetBatches()` выдаёт непрерывные диапазоны исходного потока `DrawCommandData`. Команды в одной группе имеют общие камеру, сетку, материал и удерживаемые версии ресурсов; каждая сохраняет собственные идентификатор объекта и преобразование. Диапазоны описывают совместимые экземпляры для потребителя без удаления запасного пути отдельных команд. Группировка не делает разные материалы, сетки и камеры совместимыми и не раскрывает объекты реализации.

Реализация кадра может возвращать общий дескриптор завершения подготовки из `IFrameRuntime::ScheduleDraw()`. `Engine` удерживает слот до окончания этой задачи и продолжения завершения, после чего действует обычный протокол завершения на графическом устройстве. `Update N+1` может пересекаться с подготовкой кадра N после извлечения. `Stop()` завершает задачи до уничтожения реализации кадра или арены. Снимок, арена и захваты обратных вызовов должны пережить общий дескриптор завершения; асинхронные обработчики обязаны копировать необходимые данные `FrameContext`, а не хранить ссылку на стек планирования.

Размер порции определяется нагрузкой; измеренное значение по умолчанию — 4096 элементов. Нагрузка в пределах одной порции выполняется одной последовательной задачей подготовки. Эталонный `Prepare()` вовсе избегает расходов на планирование; для текущей дешёвой модели видимости последовательное выполнение может быть быстрее даже при тысячах объектов. Решение о распараллеливании принимайте на основе измерений, а не только числа сущностей. См. [измерения производительности](../benchmarks/renderer/README.md).

## Граф рендеринга

`RenderGraphBuilder` — граница управления кадром на процессоре между подготовкой рендеринга и выполнением через `Graphics`. `Compile()` публикует неизменяемый самодостаточный снимок объявлений и не записывает команды и не отправляет работу на графическое устройство. Публичный заголовок доступен при выключенных Vulkan и GLFW.

### Объявление кадра

Для действительного `RenderFrameIdentity` создаётся один построитель. Постоянные дескрипторы изображений и буферов `Graphics` импортируются с явным исходным и конечным `EResourceUsage`. Метаданные берутся из реестра `Graphics` с проверкой владельца и поколения; нельзя подставить произвольный дескриптор вместо существующего ресурса. Импорт не передаёт владение. Повторный импорт того же ресурса завершается ошибкой, чтобы не скрывать зависимости за псевдонимами. Идентификаторы принадлежат построителю и не переносятся в другой построитель или слот кадра.

Владелец интеграции WSI передаёт `SwapchainGraphTarget` для каждого поколения полученного изображения: непрозрачный уникальный ненулевой идентификатор и фактические метаданные формата, размера, числа образцов и возможностей. Исходное использование должно быть `UNDEFINED` (явное отбрасывание содержимого) либо `PRESENT` (сохранение содержимого); конечное `PRESENT` обязательно и добавляется `ImportSwapchain`. Объект — лишь связующий токен на процессоре, а не второй цикл отображения и не физический дескриптор изображения. WSI владеет каноническим отображением идентификаторов на физические изображения и синхронизацией получения. Одно физическое изображение не может иметь два действующих идентификатора. При изменении размера или освобождении токен становится недействительным; для следующего получения создаётся новый. Графы держат слабые ссылки; уничтожение или аннулирование цели вызывает ошибку при последующей проверке компиляции/записи.

`GraphicsPassDescription` объявляет чтения, записи, цветовые и глубинные целевые изображения и копии пакетов `DrawCommandData`. Данные `RenderPlan::GetDrawCommands()` можно копировать в `DrawCommands`. Изменяемый `World`, `RenderWorld` и объекты реализации не передаются обработчикам исполнения. Метаданные целевых изображений выводятся из импорта, предотвращая противоречивые копии формата и размера.

Намерения загрузки, сохранения и очистки выражаются явно. `CLEAR` определяет содержимое всего целевого изображения; `LOAD` требует определённого содержимого и сохраняет его. `DISCARD` при загрузке делает предыдущее содержимое неопределённым; один только `STORE` его не инициализирует. Пакеты рисования не гарантируют полного покрытия изображения: результат прохода с `DISCARD` остаётся неопределённым даже при наличии команд. Следующая очистка может определить его до чтения или экспорта. `DISCARD` при сохранении всегда делает содержимое неопределённым.

### Компиляция и просмотр

Ресурсы получают версии в порядке объявления с гранулярностью целого изображения или буфера. Чтения зависят от предшествующей записи, записи — от неё и всех промежуточных чтений (`RAW`, `WAW`, `WAR`). Два чтения не создают ребра. Повторные либо конфликтующие обращения в одном проходе отклоняются; одновременное чтение как текстуры и запись в целевое изображение на месте здесь не поддерживаются. Для целевых изображений требуются соответствующие объявления записи, совместимые размеры и число образцов, допустимые сочетания формата и использования.

Явные зависимости упорядочивают независимые проходы. Ребро против направления ресурсной зависимости создаёт цикл и вызывает ошибку вместо скрытого изменения смысла версий. Устойчивый алгоритм Кана выбирает минимальный идентификатор объявления среди готовых проходов. Рёбра устраняются от повторов и упорядочиваются детерминированно. Чтение до формирования данных, `LOAD` после отбрасывания, недействительные начальные или конечные состояния и экспорт неинициализированных данных вызывают существующую ошибку `INVALID_ARGUMENT`. `UNDEFINED` допускается только как исходное явное отбрасывание, никогда — как состояние прохода или результат.

`CompiledGraph` открывает постоянные диапазоны упорядоченных проходов, используемых ресурсов, зависимостей, переходов, времён жизни и диапазонов записи. `GetResource(id)` разрешает импорт без раскрытия физической реализации. Порядок проходов, семантика использования, правила целевых изображений и начальные/конечные состояния образуют план исполнения; физические переходы выводятся отслеживателем состояний реализации. Повторная компиляция детерминирована, а старые результаты не зависят от последующих изменений построителя. Для временного хранения и снимка используются обычные владеющие векторы: нет утечки нетривиальных объектов из арены или скрытого удержания их после сброса кадра.

### Владение и исполнение

Построитель, скомпилированный граф и их память принадлежат одному поколению слота кадра. Нетривиальные объекты уничтожаются при аварийном завершении или освобождении перед сбросом арены слота. Данные графа нельзя кэшировать между кадрами. `ValidateResources(frame)` отклоняет другой слот/поколение, освобождённые или повторно использованные дескрипторы `Graphics`, а также уничтоженные или аннулированные цели обмена изображениями. Исполнитель обязан вызывать проверку непосредственно перед записью команд. Экземпляр `Graphics` должен пережить все импорты. Освобождение ресурсов, изменение размера и проверка/запись внешне сериализуются в потоке владельца.

Графы не удерживают выделенную память графического устройства или `ResourceLease`. Существующие записи использования ресурсов в кадре `RenderWorld` удерживают точные версии логических ресурсов пакетов рисования до завершения отправки. Импортированные ресурсы устройства и поколения обменных изображений принадлежат внешнему владельцу до окончания всех использующих их отправок. Отображение изображения не означает завершения исполнения на устройстве.

Исполнение графа Vulkan использует этот план, преобразует состояния через `ResourceStateTracker` и `Sync2`, а целевые изображения — через механизм динамического рендеринга. Сохраняются существующие границы отправки `Graphics` и получения/отображения WSI. Интеграция должна использовать один протокол идентичности кадра и завершения для всех активных слотов; изменение размера или устаревшее изображение аннулирует предыдущие импорты. Проверки первого треугольника и изменения размера при `MaxActiveFrames > 1` относятся к совместной интеграции исполнения графа и динамического рендеринга и не объявляются реализованными этим независимым от устройства компонентом.

### Текущие ограничения и расширение

Одна графическая очередь, импортированные изображения обмена и постоянные ресурсы, один или несколько графических проходов. Сейчас поддерживается импорт описаний двухмерных изображений RGBA8/BGRA8/D32 с одним уровнем детализации и образцом; импорт нескольких уровней запрещён до появления объявлений и отслеживания подресурсов. Форматы изображений обмена включают sRGB согласно WSI. Исполнитель повторно проверяет возможности и ограничения физического устройства.

Набор состояний использования содержит только поддерживаемые варианты. Состояния переноса описывают внешние входные и выходные состояния, а не самостоятельный интерфейс команд копирования. Запись `TRANSFER_DESTINATION` в графических проходах запрещена, пока не появится выполняемая операция переноса; переход состояния не создаёт содержимое. Не реализованы native memory aliasing, отсечение невидимых объектов, вычислительные проходы, переносы владения очередями или параллельная запись вторичных буферов команд.

### Отсечение и transient pooling

`CreateTransientImage(description)` создаёт логическое изображение без владения GPU allocation. Оно начинается с неопределённым содержимым, не имеет конечного экспортируемого состояния и живёт внутри графа. Все импортированные конечные состояния являются наблюдаемыми выходами; для произвольного побочного эффекта проход задаёт `HasSideEffects=true`. Без этого пустой проход или отдельное чтение, не влияющее на выход, удаляется.

После проверки полного DAG и содержимого компилятор итеративно обходит зависимости от последней записи каждого импортированного выхода и проходов с побочными эффектами. Чтение и `LOAD` удерживают производителя данных; `CLEAR` не удерживает предыдущую запись только из-за `WAW`. Явная зависимость удерживает предшественника. Неиспользуемые проходы, ресурсы и их рёбра исключаются из результата. Ресурсные зависимости строятся повторно после отсечения: удаление промежуточной записи не теряет WAR/WAW между оставшимися проходами. Некорректные объявления и циклы отклоняются даже в отсекаемой ветви. `GetResource` отвергает удалённые идентификаторы; проверка непосредственно перед исполнением касается только оставшихся ресурсов.

`GetLifetimes()` даёт включительные `FirstPass`/`LastPass` в скомпилированном порядке. Для transient изображений `Allocation` — индекс физического pool slot. Совместимы только полностью одинаковые extent/format/samples/usage. Одинаковый pool slot разрешён только при `previous.LastPass < next.FirstPass`; добавляются рёбра исполнения от всех использований предыдущего логического изображения к первому использованию следующего, включая независимых читателей. Импортированные ресурсы никогда не объединяются. Это повторное использование одного изображения, а не alias разных native allocations. Разные активные кадры обязаны иметь отдельные физические pools; повторное использование между кадрами допустимо только после точного GPU completion.

### План переходов и записи

`GetTransitions()` содержит семантическую последовательность обращений: resource, compiled `PassIndex`, предыдущее и следующее usage, возможность чтения attachment при `LOAD`/рисовании. Индекс `GetPasses().size()` означает эпилог вне rendering scope. Предыдущий usage — диагностическое намерение, не замена накопленным native stage/access masks. Vulkan lowering использует общий `VulkanResourceStateTracker`: он объединяет read states и формирует точные Sync2 barriers; при повторном использовании pool slot исходное физическое состояние сохраняется между логическими изображениями. Barrier policy не принадлежит features.

`GetRecordingRanges()` делит DrawCommands на непересекающиеся интервалы максимум по 64 команды; пустой проход имеет один пустой диапазон. Ranges неизменяемы и могут записываться независимо с inheritance/contexts соответствующего pass. Исполнение следует compiled pass/range order, barriers остаются на primary вне rendering scope. Параллельный Vulkan scheduler реализуется отдельно; графическая очередь остаётся baseline. Другие очереди не должны получать работу до появления capability/ownership-aware execution planning.

Compiler поддерживает описания imported buffers/images и transient images. Поддержка конкретного ресурса/формата исполнителем проверяется отдельно. Привязки transient texture к материалу, transfer payload, compute и native aliasing не добавляются этим контрактом.

Проверки контрактов процессора в `test/render_graph.cpp` охватывают детерминизм, ресурсные зависимости, явные рёбра и циклы, содержимое, проверку целевых изображений, действительность импорта и изоляцию слотов кадров; графическое устройство и окно им не нужны.

## Исполнение графа на Vulkan

`GraphPresentation` связывает неизменяемые пакеты `DrawCommandData` с реализацией Vulkan. Подсистема владеет одним устройством, `PipelineManager`, подготовленными версиями ресурсов и существующим путём получения изображения, отправки команд и отображения. Все операции вызываются из потока, в котором создан объект. Окно и выполняющий отправку `Engine` должны пережить соответствующие операции: сначала остановите `Engine` и завершите его работу, затем уничтожайте представление. При уничтожении ожидается завершение использования ресурсов графическим устройством и оконной подсистемой до освобождения подготовленных объектов.

### Подготовка ресурсов

`PrepareMesh` принимает удерживаемый дескриптор данных процессора с семантикой перемещения, проверяет индексированную топологию треугольников, выделяет буферы вершин и индексов через VMA и записывает данные в память, доступную процессору, с необходимым сбросом кэша до отправки. Рабочие вычислительные потоки не ожидают загрузки данных на устройство. `PrepareMaterial` подготавливает графический конвейер в `PipelineManager` до записи команд; создание конвейеров не выполняется внутри цикла рисования. Команды разрешаются по точным дескрипторам ресурсов, включая владельца и поколение, и их версиям. Неподдерживаемые либо неподготовленные версии отклоняются до записи нативных команд. Подготовленные неизменяемые версии остаются в памяти до уничтожения объекта представления; вытеснение, пакетная промежуточная загрузка и потоковая подгрузка относятся к последующим политикам владения, а не к этому пути.

Поток вершин имеет тип `MeshVertex`; графические конвейеры объявляют соответствующие привязки и атрибуты. Необязательный диапазон передаваемых непосредственно в конвейер констант размером 64 байта получает `ViewProjection * ComposeTransform(WorldTransform)` из `DrawCommandData` с порядком столбцов; нулевая длина диапазона означает отсутствие этих данных. Автор шейдера отвечает за совместимость шейдера и раскладки конвейера. Нейтральные дескриптор и ключ конвейера включают этот диапазон. Матрица камеры берётся только из immutable `RenderWorld`: положительный FOV задаёт perspective × inverse camera TRS, нулевой FOV сохраняет исходную clip-space камеру с единичной матрицей. Renderer проверяет параметры перспективы и обратимость масштаба камеры. Перед Vulkan push constants исполнитель меняет знак строки Y, сохраняя публичное соглашение Y-up и Z ∈ [0,1]. R4 дополняет разрешение привязок подготовленных материалов, не меняя `DrawCommandData` и отправку графа.

### Получение целевого изображения и исполнение

`Render(frame, producer)` пытается получить изображение без блокировки. Обработчик `producer` вызывается только после успешного получения реального изображения; ему передаётся новый независимый от реализации `SwapchainGraphTarget` с форматом и размерами. Обработчик компилирует граф текущего кадра. Целевое изображение теряет действительность сразу после записи команд; сохранять его между изображениями, повторными попытками или изменением размеров нельзя. Перед нативной записью проверяются идентичность кадра, происхождение целевого изображения, версии ресурсов рисования и совместимость форматов конвейеров.

Поддерживаемая R3 область: одно импортированное полученное цветовое изображение, один или несколько упорядоченных цветовых проходов, непосредственное индексированное рисование и неизменяемые подготовленные сетки и материалы. Компилятор определяет логический порядок проходов и операции загрузки, сохранения и очистки вложений. Исполнитель преобразует их в барьеры Synchronization2 и динамический рендеринг. Переходы состояния цвета учитывают чтение и запись при `LOAD` и смешивании; завершающий переход переводит изображение в состояние `Present`. Записи процессора завершаются и сбрасываются из кэша до операции передачи видимости памяти устройству при отправке в очередь. Подготовленные буферы сетки — неизменяемые неявные источники чтения для команд соответствующих версий ресурсов.

Другие импортированные изображения и буферы, глубина, асинхронные очереди и вторичная запись команд явно отклоняются, а не молча игнорируются. Общий интерфейс `RenderGraph` не меняется и допускает дополнительные пути исполнения: этот исполнитель не претендует на поддержку всех возможностей компилятора графа.

### Текстуры и привязки R4

`PrepareImage(ResourceManager&, ResourceHandle<ImageData>)` подготавливает неизменяемое RGBA8-изображение; `PrepareSampler` принимает ресурс `SamplerDescriptor`. Identity извлекается из `ResourceManager`, версия и CPU payload удерживаются через lease. Подготовка выполняется в главном потоке до запуска кадров: upload использует отдельный timeline и завершается до публикации изображения. `Render` не ждёт upload и не создаёт pipelines/descriptors. Асинхронная загрузка и streaming остаются отдельными задачами Resources.

`PrepareMaterial` разрешает `SampledImage`, `Sampler` и `CombinedImageSampler` в последние подготовленные версии, фиксирует их в immutable descriptor set и создаёт совместимый pipeline layout. `GraphicsPipelineDescriptor::MaterialBindings` описывает set zero без native handles и входит в equality/hash ключа конвейера. Пустое поле заполняется из материала; явно заданная несовместимая раскладка отклоняется. Шейдер должен соответствовать объявленной раскладке. `DrawCommandData` не меняется: точная версия материала определяет подготовленные привязки.

Для этих заранее загруженных неизменяемых изображений состояние shader-read устанавливается до кадров и больше не меняется. Они являются неявными источниками чтения подготовленного материала, как неизменяемые mesh buffers. Записи в эти изображения через graph не поддерживаются. Material buffer bindings поддерживаются низкоуровневым DescriptorManager, но пока отклоняются данным исполнителем.

Все версии image/view/sampler, descriptor sets и pipelines удерживаются до shutdown; `Path` уничтожается первым и дожидается реального завершения GPU/WSI. Поэтому logical unload и подготовка новой версии не освобождают объекты старого материала, а ошибка present после submit не теряет их lifetime. Это консервативная immutable cache policy, без эвикции и произвольного «N кадров спустя». Кэш ограничен ёмкостью descriptor pool; исчерпание возвращает ошибку, не перезаписывает in-flight sets. Для frame×worker arenas и completion-aware eviction в дальнейшем сохраняется backend boundary. `VulkanDescriptorManager::GetTelemetry()` возвращает согласованный snapshot allocation/cache hit/miss.

`GraphicsEngineSampleTextured` показывает четырёхцветный textured triangle через тот же World → RenderWorld → Renderer → DrawCommandData → RenderGraph → Vulkan путь. GLSL и готовые SPIR-V находятся в `samples/sample_6_textured/`; воспроизведение — `glslangValidator -V`. Запуск после сборки с Vulkan/GLFW и `GRAPHICS_ENGINE_BUILD_SAMPLES=ON`: `./GraphicsEngineSampleTextured` из каталога сборки. Heavy suite `GraphicsEngineGraphPresentationTests` проверяет все четыре сочетания `WorkerCount={1,3}` × `MaxActiveFrames={1,3}`, resize/suspend/restore, точные счётчики completion/recycle и logical unload texture/sampler до начала rendering. Synchronization validation ERROR приводит к провалу теста, отсутствие необходимого устройства/слоя — к явному SKIP.

`FrameIndex` и `FrameSlotIndex` не тождественны индексу полученного изображения WSI. Слоты сбрасываются лишь после точного завершения работы устройства. Статусы `NOT_READY`, `OUT_OF_DATE` и `SUSPENDED` без отправки не расходуют кадр и не вызывают обработчик. После принятой отправки результат всегда сохраняет признак завершения, даже если последующее отображение завершилось ошибкой: его нужно удержать до передачи ошибки вызывающему коду. Исключение при записи, отправке или отображении требует последующего уничтожения и повторного создания нативного пути.

### Пример треугольника и проверки

Соберите `GraphicsEngineSampleTriangle` в конфигурации `ci-vulkan-glfw` с включёнными примерами и запустите в главном потоке приложения. Пример создаёт `World` с камерой и индексированной сеткой и материалом. Один `Engine` управляет допуском кадров и рабочими задачами; его среда кадра извлекает `RenderWorld` и готовит планы `Renderer` в памяти кадра. Главный поток обрабатывает события и отображает результат графа. Каждый план регистрирует `std::shared_future` завершения до публикации. `Engine` удерживает память кадра до завершения устройства и лишь затем освобождает слот. Код примера не использует дескрипторы Vulkan или GLFW напрямую.

Пример отображает 240 кадров, изменяет размер окна и проверяет приостановку при нулевом размере, затем выводит счётчики отправленных, завершённых и освобождённых кадров. Рядом с исходниками GLSL хранятся готовые слова SPIR-V; их можно воспроизвести с помощью `glslangValidator -V`. Компилятор шейдеров во время исполнения не нужен. Тесты повторяют путь `World`/`Engine` при `WorkerCount`/`MaxActiveFrames`, равных 1 и 3, со слоями проверки синхронизации. Отдельный тест на устройстве моделирует `NOT_READY`, `OUT_OF_DATE` и ошибку отображения после отправки, сохраняя настоящие успешные вызовы драйвера. Тесты процессора проверяют ошибочные команды рисования, происхождение кадра и совместимость конвейеров. При отсутствии Vulkan, оконной среды или необходимых слоёв проверки выполняется явный `SKIP`; ошибки проверки корректности приводят к провалу теста.

### Первая трёхмерная модель

`GraphicsEngineSampleModel` загружает оригинальный `cube.obj` через `LoadMesh`/tinyobjloader и `checker.png` через `LoadImage`/stb_image. Ресурсы находятся в `samples/sample_7_model/assets`; путь по умолчанию вычисляется относительно исходного `scenario.h`, поэтому рабочий каталог запуска не важен, но исходный checkout должен оставаться доступным. Файлы созданы для проекта и распространяются под его лицензией. Ошибка чтения не подменяется процедурной геометрией: sample завершается с контекстом loader failure. SPIR-V textured-шейдеров переиспользуется из R4 без runtime-компиляции.

Мир содержит камеру на +Z, перспективу и вращающийся textured cube: 24 вершины с UV/normal seams и 36 индексов. Ресурсы загружаются/подготавливаются до запуска кадров. Worker `Update` изменяет Transform и применяет атомарно опубликованное main-thread значение aspect ratio. `Extract` вызывается после Draw checkpoint и копирует World в память кадра; `Draw` готовит команды только из snapshot. Main подаёт граф на исполнение после публикации плана. Следующий Update может пересекаться с подготовкой и GPU-потреблением старого snapshot. Future GPU completion удерживает слот до фактического завершения; shutdown сначала дренирует CPU/GPU consumers.

Модель выпуклая и замкнутая: back-face culling позволяет корректно показать её без depth attachment. Этот sample не обещает правильную окклюзию произвольных пересекающихся/невыпуклых meshes: depth execution остаётся отдельным расширением существующего GraphAttachment/DepthState API. Async asset streaming, GPU-driven rendering и новые пользовательские callbacks не входят в R5.

Сборка: включите Vulkan, GLFW и samples, затем соберите `GraphicsEngineSampleModel`. Запуск из корня: `./cmake-build-debug/GraphicsEngineSampleModel`. Sample отображает 600 кадров, выполняет resize и zero-extent suspend/restore, выводит Submitted/Completed/Recycled и проверяет равенство всех трёх счётчиков.

CPU suite `GraphicsEngineRendererTests` проверяет реальные asset loaders, topology/attributes, camera inverse TRS, ожидаемую projection, изоляцию от последующих World/resource changes, некорректные камеры/пакеты и отсутствие assets. Существующая serial/parallel preparation matrix теперь сравнивает и camera matrices. Heavy `GraphPresentation.TexturedObjModelThroughPerspectiveCameraResizeAndSlotMatrix` запускает 48 кадров на каждом сочетании workers={1,3} × slots={1,2,3} с resize/suspend/restore и обязательной validation. Ни sample, ни CPU integration tests не содержат native Vulkan/GLFW handles.

GPU-регрессия `TexturedObjCullsFarFaceAndRasterizesCameraFacingSurface` использует test-only Volk dispatch probe и настоящие occlusion queries: исходный draw куба делится на первые 6 индексов (+Z), следующие 6 (-Z) и оставшиеся 24, без изменения геометрии. На sample transform с камерой +Z тест требует видимость +Z и отсутствие samples -Z. Отрицательный контроль меняет только native FrontFace и требует обратного результата. Probe не использует mocks результата GPU, не меняет production API и уничтожает query pool после drain до уничтожения устройства. Непрецизионная occlusion query гарантирует только zero/nonzero, а не число пикселей; в локальном MoltenVK прогоне исходное CCW дало front=1/back=0, противоположное CW — front=0/back=1. Это защищает согласованность engine Y-up, Vulkan Y conversion и back-face culling.


### Многопроходный compiled plan

Исполнитель принимает также transient color images RGBA8/BGRA8 с одним образцом. Размер каждого rendering scope берётся из соответствующего attachment. `GetTransitions()` потребляется последовательно перед проходами и после последнего прохода; единый lowering семантики в `presentation/graph_state` передаёт usage общему `VulkanResourceStateTracker`. Необходимость attachment read включает `LOAD` и возможные чтения при рисовании/смешивании. Ranges используются как в последовательной записи, так и в текущем параллельном режиме с secondary command buffers.

Для каждого активного frame slot существует отдельный pool VMA images/views. Индексы allocations приходят из компилятора; одинаковые disjoint transient lifetimes используют одно физическое изображение и сохраняют native state между проходами. При новом кадре содержимое снова логически undefined. `Path` допускает запись в slot только после GPU completion предыдущей отправки; submission use records дополнительно удерживают allocations/views до completion, в том числе при ошибке present. Изменение описания заменяет cached allocation только на безопасной границе. При shutdown `Path` сначала завершает GPU/WSI, затем уничтожаются pools.

Этот color executor не разрешает произвольные Graphics imports с другого устройства и не создаёт material bindings на transient textures. Pass.Reads отклоняются до начала записи: без executable binding нельзя молча принимать SAMPLED_READ как реализованное чтение. Подготовленные неизменяемые material textures продолжают работать через прежний PrepareImage/PrepareMaterial path. Compiler остаётся независимым от данного color subset.


### Параллельная запись Vulkan

`GraphPresentation(window, presentationConfig, {EGraphRecordingMode::PARALLEL, &tasks})` использует
внешний `TaskSystem`, который должен пережить presentation. Исходный конструктор сохраняет serial.
Новый scheduler, поток WSI или отдельная GPU queue не создаются. Все методы presentation вызываются
на потоке-владельце вне worker invocation; подготовленные assets неизменяемы во время записи.

Backend объединяет соседние compiled `GraphRecordingRange` в не более `2 × WorkerCount` chunks на
проход. Число recording tasks ограничено WorkerCount, tasks забирают следующий chunk динамически,
без закрепления worker index. Проходы до 64 draws остаются inline; крупный проход целиком использует
secondary contents. Каждый secondary задаёт собственные viewport/scissor, pipeline, descriptors,
vertex/index buffers и constants. Dynamic-rendering inheritance фиксирует фактический формат
attachment и sample count; barriers и begin/end rendering остаются на primary.

Primary исполняет secondary buffers в logical pass/chunk order независимо от порядка завершения
workers. Один кадр по-прежнему даёт один graphics submit. Результаты tasks не владеют пулами:
вызов `AcquireSecondaryCommandBuffer` разрешён только внутри worker-context borrow. Буферы кэшируются
в frame-slot × worker owner; whole-pool reset и сброс курсора происходят после точного GPU completion,
а не через фиксированное число кадров. Сохраняется только достигнутый максимум буферов каждого пула.

Синхронная WSI-граница `Render` присоединяет task group на потоке-владельце до записи primary/submit.
Workers не ждут задач или GPU. При ошибке admission уже начатые siblings отменяются и присоединяются
до освобождения graph/результатов. При ошибке native recording group не публикует частичный кадр:
нет submit/completion, путь требует остановки. GPU resource use owners собираются на coordinator
до запуска workers и остаются у submission до completion; allocator/cache mutation с workers нет.
Полное перекрытие frame pipeline относится к IMPROVE-0030 и не включается этим режимом.

### Подсистема отображения

Подсистема исполняет на Vulkan скомпилированные цветовые проходы и индексированные команды рисования `Renderer`, сохраняя владение исполнением за графической реализацией. Нативная запись команд, синхронизация WSI, подготовка конвейеров и владение ресурсами графического устройства скрыты за независимым от реализации интерфейсом.

Крупные проходы могут записываться параллельно на внешнем TaskSystem; последовательный режим сохраняет тот же контракт.

Подробности: [контракт исполнения и пример треугольника](#исполнение-графа-на-vulkan).

## Инкрементальное извлечение RenderWorld

`NRenderer::NInternal::IncrementalExtraction` — внутренний поток снимков, используемый
`SceneRuntime`. Старые serial/parallel функции остаются эталонным плоским путём.
Один экземпляр принимает только одно незавершённое извлечение; разные потоки могут
независимо читать один quiescent World. TaskSystem, Resources и frame storage должны
пережить возвращённое completion. Уничтожение facade не отменяет отправленные задачи.

### Граница и версии

Engine завершает mutable producers и structural commit перед ScheduleExtract.
На этой границе extraction публикует pending dirty summary и читает immutable
ChangeSnapshot. Домены TransformComponent, CameraComponent и RenderableComponent
определяют обновляемые входы. Scoped ranges перечитывают только затронутые компоненты;
legacy mutable ссылки дают coarse invalidation. Пользователь не должен сохранять
writable ссылки для записи вне объявленной фазы: tracker не обнаруживает raw writes.

Первый кадр, смена World/поколений, изменение топологии, whole-storage invalidation
или потеря dirty history запускают полную повторную выборку. Идентификатор World,
а не адрес объекта, отделяет уничтоженный World от нового по тому же адресу.
Неизменившийся кадр не делает Query, resolve, copy output vectors или новые задачи
на объекты. Он удерживает прежнее immutable backing storage в своём FrameStorage.

Material/mesh наблюдаются один раз на уникальный typed slot/generation в каждом
извлечении, с проверкой owner identity. Это необходимо и без изменений ECS:
асинхронная загрузка, retry и unload не изменяют render component. Решение READY/skip
и ResourceLease фиксируются до отправки продолжения. Версии, прочитанные позднее,
не могут изменить уже захваченный кадр. Отсутствующий ресурс использует существующий
SKIP_OBJECT, ошибки сохраняют ResourceStatus. Stale/foreign references отклоняются.
Lease дублируется только внутренним builder без повторного acquisition текущей
версии; публичная move-only модель ResourceLease остаётся прежней.

### Иерархия и матрицы

При полной invalidation TransformResolver получает объединение всех камер и render
кандидатов, включая предков. Продолжение зависит от успешного resolver completion;
worker не вызывает Wait. World-компоненты копируются на границе и после неё не
читаются. Resolver удерживает topology lease до retirement обхода.

Итоговая матрица = resolved hierarchy world matrix × ComposeTransform прежнего
TransformComponent. Последний сохраняет своё поведение как плоское смещение
render объекта. Для старых сцен hierarchy matrix единичная. Не следует одновременно
записывать одно и то же смещение в оба представления. Точное affine значение
передаётся через RenderView/RenderObject и DrawCommandData до execution validation
и backend push constants. Shear не раскладывается в TRS. Perspective camera использует
обратную точную матрицу; clip-space camera по-прежнему имеет единичный view/projection.
Singular/nonfinite camera отклоняется. Culling/bounds сейчас отсутствуют: все кандидаты
остаются required, поэтому движение родителя не скрывает объект из-за старых bounds.

### Дельты и владение

RenderWorld по-прежнему предоставляет полный immutable снимок. GetDelta добавляет
WorldId, PreviousFrame, FullRebuild и deterministic ID списки changed/removed objects
и views. Потребитель применяет дельту только к предыдущему кадру этого потока.
Если PreviousFrame/WorldId не совпали либо FullRebuild=true, он строит состояние из
полного снимка. Списки — ID, значения находятся в текущем снимке. Изменение готовности
удаляет/добавляет объект тем же способом, что и структурное изменение.

Успешная публикация заменяет cache/cursor; exception и cancellation их не продвигают.
Пользовательские деструкторы ресурсов исполняются вне cache mutex. Reset разрешён
только idle и освобождает cache; сохранённые FrameStorage продолжают удерживать
старые payload/GPU representations независимо от Scene unload и текущего Resources.
Engine Stop сначала завершает CPU work, затем Drain освобождает cache. При ручной
отмене completion пользователь должен завершить TaskSystem work до изменения
топологии: отмена зависимой задачи сама по себе не присоединяет работающий resolver.

Для пропущенных из-за LOADING объектов сохраняются новые матрицы и состояние resolver
даже при пустой видимой дельте: последующий READY использует актуальную иерархию.

### Стоимость и проверка

Sparse изменения не создают task-per-entity. Продолжение обрабатывает batch, resolver
использует существующий adaptive traversal. При изменениях полный contiguous output
пока материализуется за O(render candidates), включая копии владения неизменившимися
ресурсами. Дельта содержит только фактические изменения матриц/версий/проекций.
Это сохраняет span API текущего renderer; persistent GpuScene/chunked snapshot —
последующее развитие. Даже static frame имеет O(candidates) сравнение выбранных
ресурсов и O(unique resources) обращений к ResourceManager; O(1) для сцены не обещается.

Регрессии Incremental проверяют WorkerCount=1/4 и MaxActiveFrames=1/2/3, old snapshots,
scoped single-object write, parent/shear, retry/hot reload, create/destroy/recycle,
missing history, смену World, capture-before-ready и failure rollback. Benchmark
BM_RenderWorldExtraction сравнивает неизменившийся кадр с parallel IMPROVE-0023:
1024/16384 объектов, 1/4 workers, режим 0 — baseline, 1 — incremental, static/single-write workload.
Результаты и команда повторения — в [измерениях](../benchmarks/renderer/README.md).

### Сериализация и остановка Engine

`SceneRuntime` использует один cache на все slots. В Engine::RunExtraction продолжение
FinishDraw зависит от возвращённого extraction handle; только FinishDraw открывает
m_updateAdmissionOpen для N+1. Terminal status TaskSystem включает retirement callable,
поэтому Admission::~Admission уже снял Busy до следующего ScheduleExtract. Draw N и
GPU работа могут продолжаться параллельно Update/Extract N+1; две mutable/extraction
фазы одного потока не пересекаются. EnginePhaseGates.EveryExtractionReaderMustRetireBeforeNextAdmission
проверяет сам gate. Интеграционный SceneRuntime тест удерживает реальный Draw N, пока
N+1 обновляет и извлекает тот же World/cache (workers 2/4, slots 2/3).

Engine::Stop завершает semantic producers и TaskSystem::WaitIdle до вызова Drain.
StopDrainsRunningIncrementalPublicationBeforeNoexceptReset удерживает именно callable
публикации IncrementalExtraction; Stop не возвращается и не вызывает cache Reset до
его retirement (workers 1/4, slots 2/3). Поэтому Reset в noexcept Drain вызывается
только idle. Отдельный CompletionFailureAfterResolverKeepsCursorAndRetriesWarmHierarchy
бросает исключение из completion после успешного resolver и проверяет retry с прежним
PreviousFrame, новой material version, корректной матрицей/дельтой и cache-hit resolver.
